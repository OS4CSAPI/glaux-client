## 1. Narrow finding: a physical equipment subject is not identical to its digital exposures

A sensing-equipment **individual** may have descriptions, aliases, models, service endpoints, database registration records, digital proxy objects, and software interfaces that provide information or actions about it. **They do not inherit identical referent, identifier, version, cardinality, state or provenance by sharing the word ‘System’, ‘Device’, ‘Thing’, ‘Asset’ or ‘Component’.** The candidate DIM should preserve the separation of *described equipment* versus *source-qualified representation and mediation roles*, while keeping actual binding details in the donor standard, future CSAPI Profile or client layer as appropriate.

**Provisional V2 synthesis—not a new class/relation:** *An individual sensing-equipment System can be described or accessed through multiple information resources and mediation services. Their identifiers and representations have source-specific meanings and scopes; representation identity is not equipment identity without a validated mapping. The represented subject may be one physical individual, a functional aspect, a virtual thing, or an aggregate, depending on the donor and evidence. An integrator must not invent sameness, physical components, capability or current state simply because a digital representation exists.*

Three **different questions** must remain open rather than becoming one invented `DigitalRepresentation` / `representedBy` class: (1) *what* physical subject is being described; (2) *which* source-defined resource, representation, service or proxy exposes what aspect; and (3) *how* that particular relationship, version, time and identifier correspondence is established. No single universal URI rule, digital twin, one-to-one mapping cardinality or model extension is adopted.

**Source scope:** **10 source-concept alignment records** from **six distinct frozen artifact IDs: 10, 34, 97, 104, 132, 144**; six source lineages, **five standards-based families plus one pinned implementation pattern (OSUS-R)**. These are **not six independent class votes**. Direct primary source clauses/files were read on each. Source ID **132** is the inventoried **WoT Architecture 1.1**, whereas **WoT Thing Description 1.1 is NOT a distinct frozen artifact**: it is explicitly called out as a supplemental **`OUTSIDE_FROZEN_CORPUS` official companion, as documented in [Step 05 ISSUE-T02-01](05_Product_Model_Kind_Alignment_v0.1_28OCT2026.md#issue-t02-01--w3c-wot-thing-description-11-is-not-a-separate-frozen-source-artifact)**. The frozen 182-entry population and all its identifiers remain unchanged.

**Evidence limit:** `PRIMARY_TEXT_CHECKED` applies only to named sections of published CSAPI Part 1 v1.0, AAS Part 1 v3.2, WoT Architecture 1.1 and supplemental TD 1.1, OPC UA Devices v1.05.0, SAREF Core v4.1.1, and pinned OSUS-R source files. The Smart Citizen counterexamples derive from commit-pinned public source code and manufacturer guidance, not an authenticated physical Kit or captured server response. Source-native meaning is distinguished throughout from V2 analyst inference, implementation design and conformance.

### ISSUE-T05-02 — source identity/alias reconciliation is not established
What constitutes *the same real-world equipment individual* across CSAPI, AAS, WoT, OPC UA, OSUS-R and vendor software must be supported by source-defined identity equivalence, valid scoped identifiers and possibly temporal/replacement rules. Different IDs may refer to one thing; the same string may be reused for different roles. **Do not presume either equivalence or separation without source proof**. CSAPI's URI-valued System UID, AAS global/specific Asset IDs, WoT mutable/contextual TD IDs, OPC UA NodeIds, OSUS software UUIDs, Smart Citizen platform IDs/tokens/MACs are **not synonymous**.

### ISSUE-T05-03 — representation aspect / proxy / current-state authority remain open
An AAS Submodel, SAREF Service, OPC UA offline configuration, WoT twin, a vendor measurement association and a CSAPI System feature can describe **different aspects**. Even if eventually linked to the same equipment, each may contain type-level, simulated, historic, cached, configured, command, or live values. The DIM might need provenance/representation-role distinctions; binding/ID/quality rules may belong to a Profile or client. No mandatory new DIM class, predicate, URI scheme, cardinality or normative `SHALL` has been justified by this step.

### ISSUE-T05-04 — OSUS-R is evidence of a *software pattern*, not a universal ontology
The frozen ID 34 is an inventory assessment of OSUS-R's Asset interface and capability model, while the actual directly inspected Java files are at the **2023 pinned revision**. The evidence supports an interface/plug-in separation, **not** a normative `AssetProxy` class shared with WoT Intermediary/AAS Shell or proof that OSUS-R satisfies a future CSAPI application Profile.
