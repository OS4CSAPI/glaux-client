## 1. The human objective and the three separate things we must deliver

The original practical problem came from comparing TRSS and OmniSense unattended sensing systems: different manufacturers organize equipment, capabilities, data, management and user-facing resource detail differently. The user wants **one genuinely useful, profile-aware OGC API – Connected Systems (CSAPI) Resource Details experience** capable of interpreting the information common to unlike sensing systems **without erasing real differences** or relying on a special parser for each manufacturer.

We are working toward three distinct results:

- **Domain Information Model (DIM):** implementation-independent, donor-supported meanings and relations for the **whole sensing System**—identity/kind, physical equipment, functional and observing roles, communications/power/software as warranted, configuration/state, actions, time and history, provenance, quality and relevant management.
- **CSAPI application Profile:** defensible and testable ways to express the accepted DIM meanings through actual OGC API – Connected Systems Parts 1–2, Sensor Model Language (SensorML) 3.0, SWE Common 3.0, OGC API – Features and other justified original standards. It must distinguish existing standard requirements from project Profile choices and openly unsupported cases.
- **Shared Glaux interpretation and evaluation:** one common semantic reader and Resource Details UI treatment, tested with multiple unlike sources and honest source→DIM→Profile/API→UI fidelity checks. A beautiful handcrafted manufacturer view or successful HTTP GET alone is insufficient.

**“System and sensor and equipment” is a provisional scope description**, not a final project title or imposed root class. V1 research, MERLIN context and the original five proposed F-01–F-05 distinctions are resources, **not authority to impose a preselected V2 model**. The final deliverable is a *publication-ready technical candidate*, not an adopted OGC standard or a claim of universal vendor conformance. See the [plain-language research history](DIM_Profile_V2_Research_Story_and_Current_Position_v0.1_29OCT2026.md) and the [earlier provisional architecture blueprint](DIM_Profile_V2_Provisional_Architecture_Blueprint_v0.1_28OCT2026.md), both historical/explanatory rather than superseding the current plan.

## 8. The recurring failure patterns this handoff must actively prevent

The full [30 October AI hallucination/research drift case study](DIM_Profile_V2_AI_Hallucination_and_Drift_Case_Study_v0.1_30OCT2026.md) governs; these are its operational consequences:

1. **No inherited chassis or automatic power-first agenda.** V2 restarted from valuable V1 resources, not V1 architecture. “Operational condition/status” was repeatedly promoted without equivalent pedigree as a synthesized V2 concept; it is not an accepted sixth foundation. Power is relevant as evidence warrants but is not privileged.
2. **Donors are not challengers to an incumbent.** Treat later contributors on their original terms. They may support, split, merge, replace or leave open a proposed meaning; never force all material into F-01–F-05, a UI tab or a favorite early standard.
3. **No inflated source authority.** A published manufacturer design/specification, a code sample, an original field record, a project fixture, a derived association, a live HTTP round trip and a fully accepted normative interoperability requirement are different categories.
4. **Seven explicit evidence labels:** **SOURCE_FACT**, **SOURCE_EXAMPLE**, **DERIVED**, **CANDIDATE_MAPPING**, **VERIFIED_RUNTIME**, **UNKNOWN**, **REJECTED_EQUIVALENCE**. Use the correct label with source, scope, identity, date and edition. UNKNOWN is neither zero nor false; absence of a relationship must not be invented as an empty object.
5. **Do not swap referents.** Manufacturer model ≠ physical serial; physical component ≠ channel; Host ≠ permanently contained part; observer ≠ reporting logger; configured default ≠ effective operating state; accepted task ≠ observed physical effect; a source station point ≠ individual probe coordinate.
6. **Keep actual time semantics distinct.** Date-only use and as-of statements ≠ precise installation timestamps; maintenance window ≠ specific swap clock time; Observation phenomenonTime ≠ resultTime; source-row timestamp ≠ proof of result publication; logger status ≠ ambient observation.
7. **Do not manufacture a comparable operating-data corpus.** Reference designs are valid for bounded conceptual analysis, **not** validation of four fully observed fielded systems. Never join incompatible examples across editions and devices into a fake installation.
