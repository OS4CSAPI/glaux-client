## 1. One-minute orientation — what the actual project is for

The motivating TRSS and OmniSense II examples showed the need for a **shared but operationally meaningful Resource Details experience** for sensing-equipment Systems integrated through OGC API – Connected Systems (CSAPI). Displaying a generic CSAPI/SensorML property list is not enough if the integration or the client loses the source's useful distinctions: installed versus optional detector/transducer, manufacturer kind versus serial-numbered individual, selected configuration versus capability, voltage versus battery estimate, procedure versus actual execution, component versus independently managed System, and so on.

The longer-term outputs are **(1) an independently publishable implementation-neutral Domain Information Model (DIM), (2) a publishable CSAPI application Profile that can communicate the DIM's relevant meanings, and (3) a profile-aware CSAPI client demonstration**. The DIM is **not** the UI, the Profile is **not** the DIM, and donor/source comparison is **not** automatically a conformance claim. The intent is common structure plus faithful source-specific detail—not vendor-specific hard-coded renderers, invented hardware states, or a copy of the V1 eight subject bins.

The working focus is on **equipment-realized Systems with a defining sensing/observing role**, without excluding their non-sensing equipment and functions. The defensible final chassis scope, umbrella domain name, root class, package architecture and Profile obligations remain **research and later decisions**, not adopted facts. OGC CSAPI `systemType=Sensor` and `assetType=Equipment` are different facets; do not manufacture a new unqualified category or force a universal superclass.

## 3. Exactly what Step 05 resolved and did NOT resolve

The donor sources support describing an individual System in terms of *reusable kind/model information* without conflating that description with the particular unit, its selected configuration, its actual observation or its health. **They do not mandate one universal `ProductModel` class.** OGC CSAPI's `systemKind` relation targets a `Procedure` used to describe a System kind/datasheet; the separately named `procedures` relation concerns methods the System can implement. AAS `AssetInformation.assetType` and CSAPI `assetType` mean different things despite similar names. An OPC UA manufacturer `Model` nameplate string is not a fully resolvable technical specification, and an OPC UA `DeviceType` represents information-model typing rather than necessarily a manufacturer product. W3C WoT `Thing Model` primarily supplies reusable interaction/interface semantics, not necessarily hardware identity.

**Documented unresolved source gap:** W3C WoT Thing Description 1.1 was inspected as an official **out-of-corpus companion** to inventoried WoT Architecture 1.1 (**artifact ID 132**); it does **not** have its own frozen artifact ID. **Do not quietly add a 183rd artifact, alter the 182-row source ledger, or infer a new mapping from its absence.** Any formal corpus expansion requires its own decision. Manufacturer model URI/version/inheritance, cardinalities, true physical-to-product joins and deployment-specific configuration remain open. No actual TRSS, OmniSense or SCK source→Profile→client transformation was tested by Step 05.
