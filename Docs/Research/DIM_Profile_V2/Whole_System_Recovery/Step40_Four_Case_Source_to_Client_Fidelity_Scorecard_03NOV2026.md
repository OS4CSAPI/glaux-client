# Step 40 — Four-case original-source → DIM → candidate Profile/CSAPI → Glaux fidelity scorecard

**3 November 2026 · Step 40 analytical deliverable · Four controlled source situations · No model, Profile, app, server or deployment repairs.**

**Standing:** This is an evidence-grounded **fidelity assessment**, not an OGC conformance test, a final profile, an assertion that all original donor standards have been adopted, or a claim that the packets exhaustively represent any whole system. **Gate E remains NOT CLOSED; Gate F remains NOT CLOSED as a complete portable source-to-native-CSAPI-to-generic-client chain.** The current controlling [43-step plan](../PLAN_DIM_Profile_V2_Whole_System_Recovery_to_Delivery_v0.1_31OCT2026.md) authorizes **Step 40 only**; [Step 41](../PLAN_DIM_Profile_V2_Whole_System_Recovery_to_Delivery_v0.1_31OCT2026.md) will separately decide targeted repairs and explicit exclusions.

## 1. The conclusion before the tables

**A common interpreter of accurately described equipment is now real, tested software, but a portable and source-authentic CSAPI Profile is not yet real.** The project has an implementation-independent [integrated DIM, R24-01–15](../Candidate_Specification/DIM.md#r24-relationship-register--one-connected-model-individually-testable-meanings), a separately drafted [candidate CSAPI application Profile, PR30-01–21](../Candidate_Specification/CSAPI_Profile.md#3-candidate-pr30-rule-index--one-cross-case-contract-with-examples-and-original-authority), four source-audited [Step 32 research packets](../Candidate_Specification/Step32_Source_Packet_Contract.md), [one unchanged Glaux source interpreter](https://github.com/OS4CSAPI/glaux-client/blob/work/details-view-20261023/src/profile/source-packet.ts), and one [existing Resource Details UI using that interpreter](https://github.com/OS4CSAPI/glaux-client/blob/work/details-view-20261023/src/presentation/resource-details-profile-test.ts). All four packets have passed real Vitest and local browser presentation checks within their **declared research standing**.

We must not confuse those four selected packets with four complete, operational systems. **Dragino, AirGradient and Campbell are manufacturer reference/design cases.** None proves an installed unit or a performed field observation. **Bennett's Point is an actual historical station case** with real source-identified equipment, two original NOAA/CDMO mean-temperature reports and several previously loaded **project experimental API copies**. Thus the absence of actual Observations for the three manufacturers is **correct qualification**, not missing telemetry the client should synthesize.

The source packet is **not the adopted CSAPI Profile format**; it is an explicitly project-authored input fixture. Its correct structural interpretation cannot authenticate whether the publisher actually issued a serial, whether a printed sample is real telemetry, whether a time/date is precise enough, or whether four API Observations are four original source events. The tests intentionally mutate source-faithful packets to make such false assertions and show that **23 coherent but source-FALSE mutations are still accepted structurally**. Those 23 negative-oracle tests **pass because the test discovers this failure**, not because the false source assertions are considered true.

The **most important new runtime success** is separate: [Step 39](Step39_ReadOnly_E2E_Validation_03NOV2026.md) actually established Node 24/full Vitest/build and real Chromium, plus read-only access to the existing Oracle-hosted 52°North CSAPI Bennett experiment. **198/198 Vitest checks**, **14/14 local source-packet browser checks**, **14/14 native Node GETs HTTP 200 JSON**, and **10/10 specialized native Bennett browser checks with 10/10 browser-to-server GETs HTTP 200** passed on the tested application commit. That proves important *software and transport* behavior, **not** the missing producer-published Profile standing/discovery, independent source authenticity, or full native OMS/SWE Observation conformance.

## 2. How the scorecard judges fidelity

The sequence is **original source → R24 DIM proposition → PR30 conditional binding / actual native CSAPI evidence → selected Step 32 packet → generic Glaux interpretation/UI**. The order matters. A correct model cannot compensate for information never collected; a complete packet cannot make its author truthful; a beautiful UI cannot validate an unsupported standards carrier.

The following words designate **different evidence dispositions**, not new ontology classes or standardized wire property names:

| Assessment | Exact meaning in this report |
| --- | --- |
| **PRESERVED (LOCAL)** | An original source fact, original literal, original scope or example standing survives in the selected packet and the shared local Glaux reader/UI, with no known contradiction **for that supplied original input**. This does **not** authenticate future arbitrary packets. |
| **SOURCE EXAMPLE** | A manufacturer-published payload/sample demonstrates an output shape/value. It is **not** a measurement made by an identified installed unit. It can be displayed as a sample but cannot create an actual Observation. |
| **DERIVED / QUALIFIED** | The project inferred an interval or relationship from separately attested sources; derivation and source precision remain visible and are not relabeled as original operator/NOAA data. |
| **UNKNOWN (SOURCE-LIMITED)** | The claimed actual state/individual/time/position cannot be established from the inspected original corpus. Correctly withheld or displayed UNKNOWN; not zero, false, current, or a universal statement that the property never exists. |
| **OMITTED FROM SELECTED PACKET** | Original material **does document a fact**, but the narrow Step 32 fixture did **not select it**, so the shared reader and its UI cannot display it from that packet. This is an **extraction/coverage gap**, not evidence the parser dropped a supplied value. |
| **NATIVE BINDING HOLD** | The DIM has a proposed meaning or conditional OGC carrier, but no exact native, standards-conformant, discoverable producer→generic-client encoding or necessary source fact has been proven. This is not automatically a server implementation defect. |
| **TESTED NATIVE — LIMITED** | A native API HTTP response and/or the **existing case-specific Bennett browser page** was truly checked. Successful transport/display does not certify that the **generic source-packet UI** discovered a native source Profile or that an OMS/SWE structure is conformant. |
| **SOURCE-FALSE COUNTEREXAMPLE** | A deliberately altered packet passed generic structural validation despite contradicting the original. A test-only source oracle rejected it. **Do not confuse an adversarial test mutation with an error in the unchanged original packet.** |
| **NOT TESTED / OUT OF SCOPE** | No authenticated installed unit, actual operation, native class, permission/effect, transport or current-state proof was supplied for the particular claim. Not a product-quality judgment. |
