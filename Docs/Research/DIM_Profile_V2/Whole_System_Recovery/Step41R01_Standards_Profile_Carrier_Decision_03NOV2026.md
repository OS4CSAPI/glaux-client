# Step 41R-01 — Standards-grounded Profile discovery and source-evidence carrier decision

**3 November 2026 · DECISION ONLY · CANDIDATE PRODUCER/CONSUMER CONTRACT · NO IMPLEMENTATION.** This is the one authorized 41R-01 increment in the [Step 41 repair plan](Step41_Release_Blocker_Dispositions_and_Bounded_Repair_Sequence_03NOV2026.md#4-six-deliberately-bounded-inserted-repair-iterations--all-pending). It is **not** an adopted Open Geospatial Consortium (OGC) Profile, newly registered OGC requirements class, new CSAPI media type, a valid deployed native resource, publisher authentication, or a passing unknown-client trial.

**Decision:** **SELECT a layered, standards-native-resource + registered Web Linking + clearly project-owned evidence-sidecar design for later falsification**. Existing OGC API – Connected Systems (CSAPI), Sensor Model Language (SensorML) 3.0, and SWE Common 3.0 resource meaning and schemas remain untouched. **RFC 8288 HTTP links**, the IANA-registered **`profile`** link relation defined by RFC 6906, and the registered **`describedby`** relation provide a defensible *discoverability* bridge. The **actual source-claim model in the linked evidence document is a NEW, versioned PROJECT PROFILE CONVENTION**, not a field already mandated by CSAPI, SensorML, SWE Common, Observations, Measurements, and Samples (OMS), RFC 6906, or a universally interpreted extension. It must be published, specified, constrained, source-tested, served and consumed before a real interoperability claim can be made. **Gate E / G30-01 stays OPEN; Gate F stays OPEN.**

The chosen design is a **conditional architecture decision**, not approval of all presently proposed PR30 semantics. If 41R-02, 41R-05 or 41R-06 exposes a contradictory original source, an incompatible existing CSAPI representation, an unsupported native format, an unsafe discovery rule or an inability to validate original assertions, **revisit this decision and retain the gate HOLD**, rather than hard-code a product identity, manufacture a time value, or claim a conformant native observation.

## 1. The human problem being solved

A client that has never been specially programmed for Dragino, AirGradient, Campbell or Bennett's Point must distinguish a **manufacturer model description** from an **actual identified piece of equipment**, a **source's printed example** from a **performed measurement**, a **project-derived association** from a source-authored fact, and **two original historical measurements** from **four old experimental API copies**. These meanings are already explicit in the four project's [Step 32 evidence packets](../Candidate_Specification/Step32_Source_Packet_Contract.md) and preserved by the common local [Glaux reader](https://github.com/OS4CSAPI/glaux-client/blob/work/details-view-20261023/src/profile/source-packet.ts). They are **not yet conveyed by one discoverable native CSAPI producer→generic client path**.

An OGC resource's valid `System`, `Procedure`, `DataStream` or `Observation` structure must remain what the original standard says it is. An integrating publisher must ALSO be able to say which original source supports a claim, its original source precision, and where interpretation is missing. Neither resource type nor provenance alone establishes truth: **original publisher/issuer**, **integrating producer**, **API server**, **individual resource**, and **client** have distinct responsibilities. A source may be explicitly *unverified* without becoming `UNKNOWN` in the sense of an unknown value.

**Meaning of “unknown-compatible client”:** an independently implemented client **that understands the published project Profile contract** but has no vendor-specific branches, hand-entered resource IDs or private producer knowledge. A general CSAPI/SensorML client that does **not** implement this project Profile is entitled to ignore project-only evidence semantics and continue to use the native standard representation. This selected mechanism is a route to test profile-aware interoperability, **not universal automatic comprehension by every OGC client**.

**Why B is chosen:** It separates **what native OGC resources mean** from **what our integrating publisher claims to know and from where**. It uses already registered link relation types instead of inventing a pretend OGC `sourceStanding` field, keeps a source-auditable record behind a machine-resolvable link, and gives Glaux a falsifiable generic discovery problem. It is **not** an end-state guarantee: it can fail at source truth, available server links, cross-origin access, schema validity or unknown-consumer portability, and each failure must remain visible.

## 4. Selected candidate producer→Profile→consumer contract (NOT yet implemented)

**Provisional short label:** *linked source-evidence description*. This is a convenient phrase, **not a newly approved domain, formal specification name or additional mandatory DIM class**. We **do not** mint a purported production Profile URI, OGC requirement URI, registered media type or namespace in Step 41R-01. All `example.org` addresses below are fictional **documentation placeholders**.

### 4.1 Native source/resource path remains authoritative for native meaning

The producer serves a genuine, schema-valid **CSAPI native resource** of the resource class actually supported (e.g., manufacturer **design kind as Procedure**, not a fabricated `System`; actual Bennett historical station `System` only if source and class/representation support exist). The native resource retains original native data types, geometry and links. A compatible Profile-aware client interprets native identity/graph/outputs using published CSAPI/SensorML/SWE semantics first, then may add source-qualification *only if it discovers and validates the separate linked description*. It may not replace native fields with an invalid historical proxy.

For every **Profile-marked native representation** that claims the linked-evidence contract, the candidate producer contract requires these additional **HTTP link relations**. These are **proposed Profile requirements**, not CSAPI universal SHALLs:

- `rel="profile"` targets an **exact, versioned, globally distinguishable Profile identifier URI**. The future project Profile specification shall be available through a stable documented route, but RFC 6906 does **not** require a generic client to dereference the profile identifier.
- `rel="describedby"` targets a **resolvable, read-only evidence description** that describes **that specific native resource** and gives an explicit `type` hint such as **`application/json`**. This is a description, **not** an `alternate` encoding of the same native CSAPI object and **not** a replacement `System` or `Observation`.
- The API **landing page** may have an additional `describedby` relation to an API-level applicability/catalog document; the **per-resource** `profile` and `describedby` links are mandatory under our *proposed* contract because a client may be handed a native resource URL directly. A root-level `profile` link **alone** must not be interpreted as applying to every response in the service.
- Follow OGC Common §6.3 native body links where their **original resource schema allows them**, and prefer the **HTTP `Link` header** on the actual resource response so this contract does **not** require injecting arbitrary attributes into native CSAPI JSON. Cross-origin browser use must expose `Link` headers to JavaScript using proper CORS settings; an HTTP 200 without script-visible links is **not** proof of browser discoverability. Verify exact media/schema and class advertisement separately.

**Illustrative only, not a real route or tested server response:**

```http
GET /csapi/procedures/reference-design-123 HTTP/1.1
Host: producer.example.org
Accept: application/sml+json

HTTP/1.1 200 OK
Content-Type: application/sml+json
Link: <https://profiles.example.org/dim-csapi/v0.1>; rel="profile"
Link: <https://producer.example.org/evidence/reference-design-123>; rel="describedby"; type="application/json"

{ /* valid native CSAPI Procedure/SensorML resource body would be here */ }
```

**No deployed host, Profile resource or actual native Procedure exists merely because this protocol example is written.** A future test must use the exact 2025 published SensorML/CSAPI schema, not this pseudobody, before claiming that actual class. Use the conformance declaration for **only OGC classes actually passed**, not a project Profile URI silently presented as an OGC class. The Profile is signalled with RFC 6906, and **producer assertions alone are not a conformance certificate**.

### 4.2 The linked evidence document's minimum project-owned meaning

The linked JSON must have a version/profile identity and a **clear binding to the one native resource being described**, including canonical resource URI, resource kind, native resource identity/UID where genuinely present, and a way to distinguish the publisher-created API identifier from original manufacturer/operator serials. A sidecar whose `describes` pointer fails to match the retrieved source resource **must not be attached by the client**. Each native resource may have its own evidence document; no back-end implementation path or new native CSAPI collection is prescribed now.

The future **project-defined JSON Schema** is to require, for the *selected source claims* rather than every imaginable device attribute, the following information. Step 32's four original research packets are the **candidate source content**, but their `dim-csapi-source-packet.s32.v0.1` format is **not automatically the served Profile format**:

| Proposed evidence element (descriptive contract, not yet a final JSON member) | Exact contract needed |
| --- | --- |
| **Profile edition and native subject binding** | A literal exact-version Profile identifier; source native resource href/UID/kind; the original source referent, with kind/reference **versus** actual identified individual/station standing. Do not create a `System` from a brochure. |
| **Issuer/publisher separation** | An original source **issuer/authority**, stable original URL/document edition/snapshot/field locator, and a distinct **integrating producer** making the claim. A content hash identifies a checked source copy; it is not by itself a cryptographic publisher signature or proof the manufacturer issued an arbitrary claim. |
| **Claim evidence and value standing** | For each source-scoped assertion identify its actual subject, field/relation meaning, original literal, unit, source locator, and **SOURCE_FACT**, **SOURCE_EXAMPLE**, **DERIVED** or **UNKNOWN** standing (project Profile vocabulary). `SOURCE_FACT` from a manufacturer's specification is a design fact, **not** an installed-unit status report. |
| **Missing and derived claims** | An `UNKNOWN` assertion includes a *reason and source scope* but no invented value. A `DERIVED` assertion names the actual original input claims and method; no converted instant becomes an original source timestamp. Absence and `UNKNOWN` are not zero, false, disabled, healthy or current. |
| **Time and precision** | Original date-only and 2024 as-of claims, original fixed EST source timestamp, **separately DERIVED** UTC values/nominal intervals and **UNKNOWN** independent resultTime where needed. Do not imply a precise Deployment interval, observed current state, or original result availability. |
| **Original event versus digital copy** | Original source event identity anchored to original publisher/source line/field/edition, **separately** from any API server Observation URI. Project `represents-same-original-event` is **project-profile semantics** requiring source test; multiple API copies must not automatically increment original event counts. |
| **Source truth/attestation status** | Explicitly distinguish source-verified against the original evidence (only if actually checked by 41R-02 tests), **producer-asserted but unverified**, and unsupported claim. This is a provenance/trust disposition, not an original sensing fact or proof of a signed manufacturer assertion. |
| **Source and native mapping holds** | Explicit unsupported native CSAPI classes/fields, source completeness selection, and exact G30/F40 references as project evaluation metadata, **not** invented native OGC state or executable privileges. |

**Terminology and cardinality** remain future Profile-contract choices, not approved code property names. A future schema may reuse Step 32's `subjects`, `sources`, `assertions`, `originalEvents` and `representations` for tested convenience, but must declare that reuse **as project-authored** and include explicit native subject binding and producer verification. Do not promote seven older analytical evidence labels wholesale into standardized OGC enums.

### 4.3 Exact user-level outcomes the later common client must recover

- **Dragino S31-LB (source reference):** one externally cabled 3 m SHT31, **two** temperature/humidity properties, design 20-minute default separate from actual unknown setting, printed 26.1 °C sample as `SOURCE_EXAMPLE`, **zero actual source observation events**.
- **AirGradient Open Air Max (source reference):** two physical PMS5003 modules at **PM1/PM2 socket names**, separate `pm01/pm25/pm10` reported property fields, other source-backed design modules/power as later selected; source examples **not** field observations.
- **Campbell CR1000X + first-generation ClimaVue 50 (separate reference products):** 14 ordered ClimaVue response positions are **not 14 physical sensors**, logger `PanelTemp` is logger-specific rather than external air, and the 31-field logger Status example is separate from a performed joined station report.
- **Bennett's Point (actual historical):** real station, **two physical EE181 serials / three calendar-day use statements**, **two original 15-minute NOAA means**, **four previous experimental API representations** of those same two; original `F_ATemp="<0> "` **including trailing blank**, independent empty `F_Record`, DERIVED period/probe association and UNKNOWN original resultTime. No exact swap instant, probe point or final single completed-mean producing System is fabricated.

**Case standing remains invariant** across all transport and data representations. This contract is not allowed to increase the number of physically authenticated units, source-performed events, available historical times or active commands simply because another JSON resource is added.

The first testable **minimal positive sequence**, expressed as plain pseudocode (not implementation), is:

```text
GET native resource URL
  -> validate native response format/identity/class advertisement independently
  -> parse registered rel=profile and rel=describedby links from this resource
  -> match an exact supported Profile version; otherwise native/raw-only fallback
  -> GET read-only evidence; verify declared media, project schema, subject href/UID
  -> preserve all source claims with original standing, raw token, time precision
  -> use one generic interpretation, no source/vendor/case-ID branching
  -> report project source-oracle truth separately from packet-shape validity
  -> render verified/producer-asserted/unknown/unsupported without fabrication
```

**Negative sequence:** wrong resource identity, unmatched version, false assertion, missing original source, unknown derivation input, broken link, unsafe redirect, absent browser CORS exposure, structurally invalid native body or source-sample-as-live attempted claim produces **FAIL / HOLD / RAW FALLBACK**, never an invented sensor, Observation, Deployment or passed conformance.

## 6. Ownership of the remaining work and explicit gates

**41R-01 has made a conditional design choice only.** Source truth is *not* repaired, native backend conformance is *not* certified, source completeness is *not* widened, and the local packet reader is *not* wired into a native Profile-aware CSAPI producer. The following responsibilities are deliberately kept in their existing separately approved increments:

- **41R-02:** formalize **project Profile** source-assertion, issuer-vs-producer, original reference and evidence verification/negative-oracle contract; keep all **23 source-FALSE** controls. Only then can a producer label an assertion source-verified by the agreed oracle. May decide to HOLD claims lacking authority.
- **41R-03/04:** original source→selected packet completeness and bounded scope repairs (Dragino/AirGradient, then Campbell/Bennett) without inventing installed units or altering the native standards.
- **41R-05:** demonstrate a **read-only native CSAPI** producer/test service with real typed links, actual HTTP headers/landing links, exact versioned Profile contract, JSON evidence-body/schema, native conformance-class/media/body validation and security/cross-origin access. - **41R-06:** use the **existing** generic Glaux reader and Resource Details frame through one native discovery path, and challenge it against unlike original source scopes and all source-false negative oracles. An in-house single consumer still is **not** equivalent to a genuinely independent third-party implementation, so report that boundary.
- **Steps 42/43:** only after gate review, produce honestly scoped candidate publication, original standard/source citations, diagrams and reproducibility, or a conditional partial result with blocker annex.

**Open risks, not resolved by RFC links:** exact canonical Profile URI/host, explicit project vocabulary/JSON Schema, accepted issuer verification/attestation model and producer governance, actual native source representation support, optional OGC requirements-class conformance, proper CORS, source-extraction completeness and truly independent third-party client behavior.
