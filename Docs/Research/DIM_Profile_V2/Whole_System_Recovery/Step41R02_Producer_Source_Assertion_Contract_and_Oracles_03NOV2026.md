# Step 41R-02 — Producer source-assertion accountability, truth oracles, and 23 negative controls

**3 November 2026 · BOUNDED PRODUCER-SIDE RESEARCH/TEST DELIVERABLE · NO NATIVE CSAPI PROFILE CONFORMANCE OR AUTHENTICATED PUBLISHER CLAIM.** The [controlling 43-step plan](../PLAN_DIM_Profile_V2_Whole_System_Recovery_to_Delivery_v0.1_31OCT2026.md) authorizes **41R-02 only**, following the [41R-01 conditional `profile` + `describedby` source-evidence carrier decision](Step41R01_Standards_Profile_Carrier_Decision_03NOV2026.md). This step **does not create the native served sidecar**, alter a candidate Domain Information Model (DIM) relationship or proposed CSAPI Profile rule, expand source coverage, edit Glaux code, write Oracle/52°North resources, issue device Commands or deploy Cloudflare.

**Decision:** an integrating producer must have a **claim-level source-evidence and verification record, separately distinguish the original issuer from the producer, and run independent *source-scoped* truth oracles before calling selected evidence consistent with original material**. A packet's JSON shape, `SOURCE_FACT` flag, source-issuer string, content hash or `profile` link alone cannot authenticate its claims. Until actually verified, the correct producer/consumer assertion is **PRODUCER_ASSERTED_UNVERIFIED**, not “NOAA authenticated” or “manufacturer verified.” The **source-verification process below is a proposed PROJECT Profile convention**, not an inherited OGC `SHALL` or a new SensorML/SWE class.

**Actually executed this step:** one new [standalone read-only producer source-oracle program](step41r02-source-oracles.cjs) evaluated four byte-preserved selected packets and the previously frozen Bennett source selection in a JavaScript V8 test execution (no file writes except this committed research script). **4/4 unchanged packet positive source-ledger checks PASS; 23/23 previously documented source-FALSE mutations detected (3 Dragino + 4 AirGradient + 5 Campbell + 11 Bennett); 4/4 *additional* issuer/authority-spoof negative controls detected.** These are **31 bounded expected outcomes**, not a newly executed Node/npm/Vitest/CI/browser run, not the Step 39 198 tests rerun, and **NOT cryptographic or independent live re-acquisition of all original materials**. Each mutation is generated **transiently in memory**; the original four selected packet JSON files and frozen source evidence were not edited.

## 1. Why this is essential to the actual client problem

The shared Glaux reader has already demonstrated it can preserve **the meaning of the information it was given**. The reader cannot independently know whether the producer made up a third SHT31, elevated an AirGradient example into a performed measurement, converted Campbell's 14 output positions into 14 physical sensors, or manufactured Bennett's original `resultTime`. Steps 34–37 proved this with 23 coherent but false mutations that passed structural parsing while independent **case-specific original-source oracles** detected them. [Step 40 scorecard §7.1](Step40_Four_Case_Source_to_Client_Fidelity_Scorecard_03NOV2026.md#71-three-noninterchangeable-failures-revealed-by-this-scorecard).

The selected **41R-01 carrier** can make a source-evidence description discoverable using typed Web links, but this says **nothing about whether the described facts are true**. Therefore source assertion and verification are **producer-side responsibilities** supported by source-origin/edition/locator/record integrity; the generic client recognizes the producer's explicitly disclosed verification status and conservatively presents **unverified / unsupported / UNKNOWN** without four proprietary manufacturer programs. Published source facts, issuer-signed evidence, source-verified producer assertions, and provider-declared but unverified claims are distinct.

The **43-step goal remains unchanged**: two publication-oriented candidate artifacts (implementation-independent DIM and separate CSAPI Profile) and a single useful, generic Glaux Resource Details experience that meaningfully preserves unlike systems. A source truth gate is necessary but still insufficient for interoperability without the later read-only **native** producer and **one generic** client tests in 41R-05/06.

## 3. Exact producer assertion/accountability contract (project candidate; not adopted OGC vocabulary)

**Producer's contract identity:** the integrating producer is the responsible party who creates or serves the **new project source-evidence description**, while the original `source.issuer` names the manufacturer, operator or archive who actually published the original. A producer claiming an original issuer **must** provide a resolvable exact source URL, immutable edition/commit or captured snapshot identity where available, original native locator, original value and unit/lexical form, date/as-of precision, and the specific person/process/test authority attesting to the extraction. A Git blob or SHA-256 verifies **bytes of a previously held copy** when those bytes are independently available; **it is not the publisher's signature, an endorsement or a proof the content truthfully describes an installed unit**.

**For each selected assertion**, the future sidecar will have to associate these *conceptual fields* before the final wire-schema key names are chosen: (a) native CSAPI resource identity and the real-world referent it represents; (b) **original source issuer/authority**, edition, original URL, native heading/field/row locator, capture date and optional recorded hash; (c) **integrating producer** name/authority and test/extraction procedure; (d) **SOURCE_FACT**, **SOURCE_EXAMPLE**, **DERIVED**, or **UNKNOWN** *semantic claim standing* with original raw token/unit/subject; (e) the source-oracle check result and exact reference/case-specific predicate, or a reason no original verification could be performed; and (f) for DERIVED, its input claim IDs and transformation method, with original-event vs server-copy identities separately described. These are **proposed project Profile concepts**, not native OGC members, unregistered requirements classes or a newly adopted final JSON schema.

**Attribution is independent of claimed standing:**

| Verification disposition (PROJECT proposal only) | What the producer actually demonstrated | Generic Profile-aware client's permitted wording |
| --- | --- | --- |
| **CONTROLLED_SOURCE_CONSISTENT** | A *specified selected claim* matches a source-scoped, separately indexed original evidence record/snapshot and an executed source oracle, with exact original and test references. The project may still lack an issuer signature or freshly verified live source. | “Consistent with this cited controlled source selection / producer source check,” **not** “cryptographically authenticated by manufacturer/NOAA.” |
| **PRODUCER_ASSERTED_UNVERIFIED** | A producer has made a coherent statement and named an issuer, but the original content, edition, extraction or verification is not independently accessible/checked. | “Producer reports this; original-source verification unavailable.” Retain the source assertion and uncertainty; **do not mark confirmed**. |
| **CONTROLLED_SOURCE_CONTRADICTED** | The specific selected assertion conflicts with a documented original source/oracle, e.g., a third probe, altered QA, shifted period or printed sample promoted into an actual act. | Must **not** be presented as verified source fact. Display contradiction or withhold Profile-qualified mapping and preserve raw record for inspection. |
| **SOURCE_INSUFFICIENT / NATIVE_BINDING_HELD** | Even the inspected original cannot establish a required fact (e.g., Bennett independent resultTime, precise EE181 swap, final mean producer; reference cases have no real installed unit). | Display **UNKNOWN/unsupported** for the unsupported fact; no synthesized timestamp, serial, observation, Deployment or command. |

**Issuer signature trust is explicitly a remaining HOLD.** The verification statuses above are **source-audit dispositions**, not original publisher-signed assertions, W3C provenance certification, mandatory SensorML attributes, or authenticated Web identity. For arbitrary future producers, the chain of custody or a separate accredited verification process would be needed to say more. **A customer/client cannot infer verified source trust from `https`, a `profile` link, `source.issuer`, original-looking URLs or a local JSON parser's `accepted:true`**.

**Source truth versus producer truth distinction:** the manufacturer/NOAA publisher is authoritative only for what its original material actually records, *at the original evidence level*. The producer is accountable for faithful extraction, precise claims, original identity scope, raw preservation, inferential transformations, completeness declaration and native serialization. The public API host is not automatically the original manufacturer; the consumer is responsible for validating selected Profile version, evidence-to-native subject, traceable standing and handling mismatch. Unsupported issuer authentication must be visibly reported as **not performed**.
