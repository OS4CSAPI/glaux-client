## 1. Decision and scope in ordinary language

The original problem is to let **one CSAPI/Domain-Profile-aware Resource Details interface** describe substantially different sensing systems usefully and faithfully. That requires three things which the recent work has correctly separated: (1) the *source* must establish the equipment, value or relationship; (2) a producer must publish it through a documented, valid, discoverable standards/Profile interface with accurate provenance and qualifications; and (3) an unfamiliar compatible client must recover the intended meaning through a common path. A correct local JSON reader is not proof of the second or third proposition.

The first part is materially advanced: the qualified R24 DIM distinguishes reference designs from individuals, physical components from fields and functions, capabilities from actual acts, and two original Bennett observations from four experimental API copies. Four selected Step 32 packets passed shared local parsing and Resource Details browser tests. The real deployed Bennett service also passed a **separate, previously specialized** live read-only path in [Step 39](Step39_ReadOnly_E2E_Validation_03NOV2026.md); the tested app source revision was **60a22d66e3481f6d0832330bfc0ae2c2788ba211**. GitHub Actions [41609815744](https://github.com/OS4CSAPI/glaux-client/actions/runs/41609815744) ran **198/198 Vitest, 14/14 local Chromium source-packet checks, 14/14 native Node GETs and 10/10 specialized live Bennett Chromium checks with ten browser-to-server GETs**. This is valid software/transport evidence but **not one generic server→Profile→unknown-client path**.

The four case situations are **not equal**. Dragino S31-LB, AirGradient Open Air Max, and Campbell CR1000X + first-generation ClimaVue 50 are **manufacturer reference/design cases with zero source-established field observations or authenticated installed individuals**. Bennett's Point is a **real historical continuing station**, with two individual EE181 probes serving three date-qualified statements, two original NOAA/CDMO April 2024 means (29.1 and 27.3 °C), and four prior project API representations of those same two originals. The original Bennett source does **not** establish the precise April 16 exchange instant, individually surveyed probe coordinates, an original independent resultTime, or the definite completed-mean DataStream producer. These source limits may not be repaired by inventing data.

**Publication and claim decision:** A source-qualified candidate DIM and a clearly labeled **incomplete Profile research draft** may be exposed for technical discussion with all holds visible. A defensible **Profile candidate for external interoperability review** needs at least a selected/implemented portable carrier, accountable producer assertions, adequate declared whole-System coverage and a common native client test; these conditions are **not satisfied now**. Neither an adopted OGC Profile, a current Cloudflare deployment of Step 38, fully native historical OMS Observations/Deployments, universal four-system operational interoperability, nor executable management may be claimed. If repair evidence cannot support the intended Profile claim, Step 42 must publish a **qualified partial result with unresolved blockers**, not silently relax the criterion.

## 3. Original-standard constraints checked during this decision

1. **CSAPI Part 1, OGC 23-001 v1.0, §19.2.7, Requirement 100** explicitly maps hardware equipment **Procedure/datasheet** descriptions encoded in SensorML to **PhysicalComponent or PhysicalSystem**; this does not turn a manufacturer reference into an installed individual or allow arbitrary position. Part 1 identifies separate System, Procedure and Deployment requirements classes and SensorML representation requirements. **Candidate descriptive tests should retain this design-vs-instance distinction in actual resource types**, when those classes are supported and properly advertised. [Original published Part 1](https://docs.ogc.org/is/23-001/23-001.html).
2. **SensorML 3.0, OGC 23-000, §8.2.2.1, Requirements 9–10** permits separately namespaced domain-specific extension content but explicitly says **ordinary SensorML-compliant parsers are not required to understand/utilize it**. Therefore an unspecified extension property or made-up sourceStanding field alone **cannot** establish Profile interoperability. A genuine Profile must separately define its own discoverable contract, producer obligations and client acceptance test, while preserving native SensorML behavior. [Original SensorML 3.0](https://docs.ogc.org/is/23-000/23-000.html).
3. **CSAPI Part 2, OGC 23-002 v1.0, §9.2 and §9.7** requires one producing System association for a DataStream and source-defensible Observation attributes. Its default JSON Observation **phenomenonTime and resultTime** are required DateTime properties; **Req 97–98** and the optional SWE Common JSON class **Req 109–111** impose format-specific schema/body requirements. A JSON response and an application/swe+json header by themselves cannot satisfy those obligations. This does **not** prove the tested server wholly fails all Connected Systems operations; it identifies the precise additional tests required for claims. [Original published Part 2](https://docs.ogc.org/is/23-002/23-002.html).
4. **OMS 3.0 original** is preserved as a [198-page Drive original and page-marked text](../Primary_Sources/OGC_20-082r4_OMS_3.0.0.md). Do not claim its original Observer, resultTime, resultQuality, Deployment or period requirements are satisfied through a custom archival-report DataRecord or a project surrogate. The full standard must govern a future positive native Observation claim.
5. **Current source packet and reader** retain source examples, DERIVED and UNKNOWN as **local project values**, with no genuine producer authentication. A third-party client cannot distinguish true original-source issuance from false provider claims using local structural JSON Schema validation alone. Exactly **23 adversarial mutations** illustrate this, and their source-oracle detection belongs in producer provenance/conformance tests rather than four vendor branches of Glaux.

This is **not** a Step 41 choice of exact OGC link relation, namespace, API path, new mandatory field, client class, adopted Profile URI or implementation architecture. Those choices require the bounded **41R-01** source-and-standard decision and subsequent tests. Read actual published clauses, not only project commentary, before selecting them.
