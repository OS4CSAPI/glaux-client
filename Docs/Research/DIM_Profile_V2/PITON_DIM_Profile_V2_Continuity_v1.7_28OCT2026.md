## 1. What we are building, and why

The objective is **(1) an implementation-independent, publishable Domain Information Model (DIM), (2) a publishable CSAPI application Profile, and (3) a profile-aware CSAPI client** that can use their semantics to present a **common, understandable System Resource Details experience** across different vendors while retaining what is genuinely different about the equipment. Initial **TRSS and OmniSense** manuals/screenshots showed that a generic standardized-resource listing can be less useful than each vendor's own rich interface. The study asks whether existing standards donors can provide a defensible conceptual **“chassis”** so integrators and clients can preserve the intended meanings without custom hard-coding every vendor screen. **Do not assert that CSAPI inherently loses data:** the loss could be in vendor→CSAPI mapping, missing source data, or client understanding/rendering. The real test will need actual producer representations and real client behavior.

The focus remains provisionally **individually describable, equipment-realized Systems whose defining operational role is sensing/observing**, with non-sensing support functions retained. **Do not invent or adopt an overarching name, new root class, or whole-system scope based on this shorthand.** Published CSAPI `systemType=Sensor` and `assetType=Equipment` are distinct source facets. DIM semantics are **not** a UI tab layout, raw JSON encoding or a copy of the V1 eight information subjects. The eventual domain name/scope/chassis/class/module architecture is still to be **discovered and defensibly decided from donors**, not fixed by research notes. Reuse donor-native meanings and explicit declared relationships, distinguish source/dependency edition, and never count source artifacts as independent donor votes.

## 3. UI and source-to-meaning lessons that must not drift

- **TRSS:** two separately indexed detector choices (Detector 1 SEISMIC/ACOUSTIC; Detector 2 IRID-II with 0-degree reported orientation) and **source estimator 100% remaining capacity** with **“collecting data”** status and source inputs. This is a **historical synthetic transcription** of indexed evidence, **not** an authenticated configuration or measured voltage.
- **OmniSense:** Core2 has **five source-reported transducer labels**, not five authenticated physical child Systems. **Separate** Core5ADS reports **15.43 V DC**, an **unverified literal source clock** and **six individual diagnostic Pass labels**—not a percentage or one global readiness result. Do not merge Core2 and Core5ADS.
- **Smart Citizen Kit 2.3:** the **cabled PM module is inside the normal kit enclosure**; the SHT31 has temperature/humidity outputs, the AS7331 multiple UV outputs. Manufacturer product alternatives/firmware code **do not** establish actual installed parts, methods executed or observations. Smart Citizen backend `Component` is a **Device–Sensor-definition association**, not a physical IC/subsystem, and source registration IDs/tokens/MACs do not prove equipment UID.
- The deployed [candidate Resource Details prototype](https://glaux-client.pages.dev/?page=resource-details-profile-test) is **early and not yet close to completion**: only a locally authored **31-key term-suffix interpreter** over static design/fixture facts, compared against a deliberately simple generic inspector. The rulebook can falsely recognize another namespace with the same final URI component; it does not validate full term/group/datatype/code-space/subject context on that path. **Six Core5 diagnostic fields remain uninterpreted**. Some literal provenance is only available via raw mode. The recorded Cloudflare production build/test success is **not a browser-driven semantic test**, **not live CSAPI**, and **not a published Profile**. The app branch was **not touched** by Steps 01–12.
