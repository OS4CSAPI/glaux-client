## 1. Executive question and finding

**Question:** Can the reviewed candidate meanings—individual System, reusable kind/model, implementable Method, actual Observation, constituent/Subsystem standing and digital representation identity—be accommodated by the existing OGC standards, **without equating incompatible things or fabricating fielded Smart Citizen Kit data**?

**Result:** **The core distinctions have substantial DIRECT semantic accommodation in the standards.** CSAPI Part 1 distinguishes an individual System, its kind/datasheet, Methods it can implement, subsystems and their contextual Deployments. Part 2 adds producing Systems, DataStreams, Observations, associated actual Procedures and SystemEvents. SensorML 3.0 supports progressively detailed physical/process descriptions, reusable types, Methods and configuration. However, **direct semantic support is not the same as a lossless implementation mapping**; some case-specific software/database relationships and physical-part granularity require explicit decisions. And **no real SCK2.3 individual, installed sensor inventory, method execution, actual observation or source-to-service identity join has been verified** (I03 F001–F060, I04 GAP-01–GAP-06, I08 DR01–DR08; Open Geospatial Consortium 2025a, §§ 8–13, 19; 2025b, §§ 7–8; 2025c, §§ 9, 12).

**Gap verdict at I11:** **ZERO DEMONSTRATED NEW CSAPI/SensorML SEMANTIC GAPS IN THIS BOUNDED SLICE**. This does **not** prove that the standards satisfy every possible future DIM need. It says the evidence examined has not established an inadequacy that warrants minting a new class or a normative profile requirement. The hardest remaining issues are **verified identity association, source-specific digital granularity, component/System standing, and execution provenance**—some are missing input evidence, others are legitimate future mapping choices.

## 2. Interpretation rules

Every row below distinguishes the **source standard's capability** from what we know about Smart Citizen. Analysis identifiers A01–A12 are **not** DIM entities, new classes, or profile requirements.

- **DIRECT:** Explicit standard resource/attribute/association supports the selected meaning. Availability may require its own optional requirements class.
- **DETAILED CARRIER:** SensorML or a separately selected encoding can carry more structural detail than a base CSAPI resource. This is not automatically a base property or mandatory service feature.
- **PARTIAL / MAPPING DECISION:** Relevant resources exist, but source-to-carrier relation or granularity is not yet established as lossless. This is not necessarily a semantic defect.
- **NO SOURCE INSTANCE / NOT TESTED:** The source has no verified physical kit, measurements, installed configuration or positive digital identity join to populate the relation.
- **NO GAP DEMONSTRATED:** Current evidence cannot justify a new V2 class/predicate, profile SHALL, or claim that CSAPI cannot represent the meaning.

**Requirements-class discipline:** Part 1 has separate System Features (§ 9), Subsystems (§ 10), Deployment Features (§ 11), Procedure Features (§ 13), GeoJSON (§ 19.1) and SensorML (§ 19.2) requirements classes. Part 2 separately defines Datastreams & Observations (§ 9) and System Events (§ 12), among others. A capability described *in the standard* does **not** imply that any particular service has implemented it. We have not found a deployed CSAPI representation of the Smart Citizen Kit.

## 4. Meaning-preserving conclusions and limits

### 4.1 The System identity carrier exists; the case has no System instance to populate

Part 1 § 9.2.2, Table 4 makes **uniqueIdentifier**, **name** and **systemType** required, with **assetType** optional. The distinction between System UID and local resource ID/URL is explicit in §§ 8.4–8.5/9.3. The standard requires URI validity and server-wide UID uniqueness; global uniqueness and persistence/URL independence have distinct **recommendation** standing. This is enough to preserve the *real-world subject vs description* distinction, but **does not establish a physical SCK2.3 identity**. Assigning notebook integer **18486** as a physical serial, manufacturing a UUID, or treating **SCK2.3** as a serial would falsify the case rather than demonstrate a successful mapping (Open Geospatial Consortium 2025a, §§ 8.4–9.3; I04/I08/I10).

### 4.2 Kind description and implemented Method already have different links

Part 1 § 9.2.2, Table 5 clearly defines **systemKind** (a single kind-description **Procedure** target) and **procedures** (list of Procedures the System can implement). Part 1 § 13.1–13.2 allows Procedure resources to describe *either* a datasheet or a methodology. In the specified SensorML encoding, § 19.2.5 **systemKind maps to typeOf**, while **procedures** remains its own link; § 19.2.7 provides the Procedure representation. **SensorML ProcessMethod** (§ 8.3.2) and **AggregateProcess** (§ 8.4) offer detailed methodologies when warranted. Source-native *association roles*, not necessarily source-native *carrier classes*, make the distinction. **No V2 ProductModel class or mandatory extra Procedure class is justified** (Open Geospatial Consortium 2025a, §§ 9.2, 13, 19.2; 2025b, §§ 8.2–8.4).

The SCK2.3 technical product description is a plausible **kind-description source**; firmware acquisition routines are plausible **method-description evidence**. Neither supplies an already identified CSAPI Procedure resource, fielded Kit association or executed event.

### 4.3 Process components and CSAPI subsystems answer different questions

The normal SCK2.3 assembly includes two mating boards and an **in-enclosure cabled PM module**. SensorML supports a **PhysicalComponent** or an intentionally decomposed **PhysicalSystem** with physical or nonphysical process components and connections (SensorML §§ 8.4–8.6). In contrast, a CSAPI **Subsystem** is a full **System** resource (§ 10.1–10.3). **A detailed SensorML process component is not automatically an independent CSAPI System; a software Device–Sensor record is not automatically a physical process component.** A cable is not proof of temporal Aggregation; physical attachment is not proof of independent managed identity. Different source granularities must remain visible (Smart Citizen 2026; I07 CMP02–CMP08; I08 DR05; Open Geospatial Consortium 2025a, § 10; 2025b, §§ 8.4–8.6).

### 4.4 An available procedure cannot be promoted into a historical Observation

Part 2 § 9.2 allows DataStream-to-System and optional Procedure association. Part 2 § 9.7 requires a DataStream and actual Observation time/result fields; optional Procedure/parameters can describe how it was produced. Multiple observed properties can occur in **one** Observation, eliminating any need to invent one hardware sensor per output channel (Open Geospatial Consortium 2025c, §§ 9.2, 9.6–9.7). The **sc_air** blueprint and frozen firmware show *method availability in code*, but the example notebook has **zero saved results** and no verified physical producer. **No result, timestamp, source provenance or historical method-use association can be populated**. If a future profile needs mandatory method provenance, that would require a distinct, evidenced interoperability argument, not an invented I11 requirement.

### 4.5 Detailed configuration is available through the correct SensorML layer

SensorML § 8.2.9.3 (typeOf/general-versus-specific process) and § 8.8 (configurable process, settings, modes) support distinctions among product options and applied instance configuration. The SensorML **Deployment representation** of Part 1 § 19.2.6 can include deployed-System configuration, but **base CSAPI Deployment** attributes/associations in § 11.2 do **not** automatically include a configuration field. This is an important **carrier qualification**, not a reason to create a DIM DeploymentConfiguration class. No actual SCK2.3 configured state, firmware version, installed SEN5X variant or deployment has been verified (Open Geospatial Consortium 2025a, §§ 11.2, 19.2.6; 2025b, §§ 8.2.9.3, 8.8).

### 4.6 Digital identity is not resolved by a field name

The official Smart Citizen advanced-station guide distinguishes a physical Hardware/Station ID from a changeable platform kit/device ID. That guidance is **not proof of a hardware ID for every basic SCK2.3**. The backend Device, MAC, UUID and token have separate software/communications roles; a matching vendor string cannot prove physical identity (I05, I08). CSAPI's System UID helps an integration **once the real-world referent is established**; the standard does not auto-resolve arbitrary proxies, records, credentials or cross-service aliases. The question of a source-to-System evidence join belongs in **future validation, mapping/provenance policy and perhaps eventual binding**, not a universally presumed new DIM **DigitalRepresentation** class (Open Geospatial Consortium 2025a, § 8.5; Smart Citizen 2026).

No proposal for profile SHALL/SHOULD, new equivalence predicate, or DIM module is justified by this iteration. A **potential gap** must be demonstrated by a source-supported requirement whose meaning cannot be faithfully represented using a selected OGC carrier, not inferred from missing input data or a dissimilar word.
