## 1. Executive result — did the five findings work together?

**Yes, at a bounded, inspectable product/design and software-architecture level. Not yet as a real individual sensing-device interoperability demonstration.** The prior distinctions are consistent when applied to **the actual Smart Citizen Kit (SCK) 2.3 design, its separate physical assemblies, published platform behavior, and available source code**. They also prevent concrete misreadings that would arise from merging data according to identical-looking names.

The most revealing conflict is **not** between donor standards. It is **inside this manufacturer's software versus hardware vocabularies**. The hardware instructions use components for the physical **Data Board, Urban Board, mounted sensing ICs, cabled particulate-matter module and battery**. Yet the published Smart Citizen API backend has a model literally called `Component` whose purpose is **a database association between one platform `Device` record and a `Sensor` definition**. It exposes values and measurement metadata; it does **not** establish an independently identified hardware board or module (Fab Lab Barcelona 2026c, original code below). This is a material integration trap: mapping every digital `Device.components` entry into a physical CSAPI `subsystem` would invent equipment structure absent from the source.

A second concrete issue is **identifier multiplicity with different meanings**: manufacturer product generation `SCK2.3`, DIY registration aid, a site `device ID`, an advanced-station physical `Hardware ID`, a MAC address, a backend `uuid` field and a device authentication token do **not** automatically denote the same entity. For advanced stations the documentation explicitly says the platform page ID can change when hardware is re-registered (Smart Citizen 2026; F047–F050). The backend's MAC reassignment behavior makes the danger visible in software. But neither statement proves any physical-unit association for the four unexecuted notebook device IDs.

**Gate A remains CONDITIONAL:** no authenticated physical serial/Kit, unit-specific installed PM option, returned device data, validated site ↔ hardware mapping or real observation. Accordingly the result is **a defensible semantic mapping and error-prevention exercise**, not a completed physical/digital identity linkage or validated DIM class model.

### 2.1 Crucial software-component versus physical-component non-equivalence

The backend `Component` object's definition is **not just an accidentally reused name**: the source's opening comment explicitly describes the association, and `ComponentPresenter` exposes the associated `sensor` with time/value fields (Fab Lab Barcelona 2026c, [Component model lines 1–7](https://github.com/fablabbcn/smartcitizen-api/blob/25a524cbfb036f8950c247b847d8884a4e776297/app/models/component.rb#L1-L7); [Component presenter lines 10–27](https://github.com/fablabbcn/smartcitizen-api/blob/25a524cbfb036f8950c247b847d8884a4e776297/app/lib/presenters/component_presenter.rb#L10-L27)). This confirms that a software-integrator's `components` collection is **at least partly a view of sensing/data channels**. It does **not** prove the existence of one uniquely identifiable circuit, transducer, or removable physical module per row.

That distinction reconciles I07's physically sourced assembly with I06's supported measurement channels: **one SHT31 chip can serve temperature and humidity; one AS7331 can serve UV-A/B/C** ([D01 sensor-to-channel associations](https://github.com/fablabbcn/smartcitizen-docs/blob/0a18bc0bd372d2bcedfca5bc5e6109f88ea8519f/docs/hardware/kit/index.md#L86-L96); Smart Citizen 2026), while the backend software can expose sensor/data associations differently. A representation's decomposition does not dictate a hardware breakdown. **This is the strongest direct practical finding of I08**, and a test that the fourth and fifth concept passes actually help rather than duplicate words.

### 2.2 Hardware reported by software is not independently authenticated hardware identity

The official backend `Device` model composes its displayed `hardware_version` from an override or an optional `hardware_info['hw_ver']`; `DevicePresenter` can expose that representation, alongside the record's `id` and `uuid` (Fab Lab Barcelona 2026c, [Device hardware/version logic](https://github.com/fablabbcn/smartcitizen-api/blob/25a524cbfb036f8950c247b847d8884a4e776297/app/models/device.rb#L306-L329); [Presenter exposed digital fields](https://github.com/fablabbcn/smartcitizen-api/blob/25a524cbfb036f8950c247b847d8884a4e776297/app/lib/presenters/device_presenter.rb#L14-L16)). Those fields are potentially useful **source metadata** for a later real integration. But they are **not proof that a real PCB was inspected**, and the presence of a `uuid` attribute does not establish a CSAPI-compliant physical System `uniqueIdentifier`. Likewise the auth `device_token` is a **credential**, not evidence of durable equipment identity. A version string from the frozen firmware source is also not readback from a specific fielded Kit (I04, FLAG-06).

The advanced calibration guide's physical `hardware ID` serves a **narrower, specific role** linking calibration and hardware versions; the platform's record ID serves a different registration lifecycle (Smart Citizen 2026; [calibration ID distinct from platform ID](https://github.com/fablabbcn/smartcitizen-docs/blob/0a18bc0bd372d2bcedfca5bc5e6109f88ea8519f/docs/guides/data/handling-calibration-data.md#L18-L25)). A backend MAC-address transfer callback supports that records can be reassociated; it does **not** prove a particular MAC uniquely identifies a lifetime-long System or that any of our candidates re-registered.

### 2.3 Published software architecture is not a demonstrated proxy, twin or interoperable resource

The vendor says its platform accepts Kit uploads, retains separate metadata and readings, presents them through an API, website and CSV export, and can support advanced software processing (Smart Citizen 2026; [API and MQTT/HTTP architecture](https://github.com/fablabbcn/smartcitizen-docs/blob/0a18bc0bd372d2bcedfca5bc5e6109f88ea8519f/docs/data/data-platform.md#L20-L35); [metadata, readings, frontend](https://github.com/fablabbcn/smartcitizen-docs/blob/0a18bc0bd372d2bcedfca5bc5e6109f88ea8519f/docs/data/data-platform.md#L54-L73)). Those are **digital mediation, interface, storage and data-processing roles**; they do **not establish** that Smart Citizen implements a **W3C WoT Intermediary**, an **Asset Administration Shell**, an **OPC UA Device Host**, an **OGC CSAPI System endpoint**, or a conventional **digital twin**.

Our frozen notebook references platform IDs **18486, 18487, 18488 and 18489** while calling a Python data client and naming an `SCK2.3_ENCLOSURE_TEST`. Its code cells have **no saved execution output** (I03 F058–F059; [notebook source and IDs](https://github.com/fablabbcn/smartcitizen-data/blob/4f024f4d42cb40c2cd515062ee7e4815bd2798eb/examples/notebooks/learning/01_basic_data_exploration.ipynb#L155-L171); Fab Lab Barcelona 2026b). Neither this notebook nor the separately saved `sc_air` blueprint demonstrates a returned digital record, actual linked Kit or method execution. The advanced blueprint's software channels also cannot be silently promoted to **physical electrochemical sensors in the base Kit**. **No source-verified identity join is available to perform.**

## 4. Donor-native interpretation and binding ceiling

**OGC API – Connected Systems Part 1, version 1.0 (published).** Its `System` describes an individual subject and has a required `uniqueIdentifier` independent of the server-local resource URL (a persistent URI is **recommended**, not automatically proven). That standard separates `systemKind`—a description of what kind of System it is—from `procedures` describing methods the System can implement, and §§ 10.1–10.3 distinguish integral System subsystems from non-permanent deployment/aggregation. **None of those standard fields may be populated as real-unit facts merely from SCK2.3 product literature or the unexecuted notebook.** There is **no verified CSAPI System/resource mapping for this Kit** (Open Geospatial Consortium 2025, §§ 8.5, 9.2.2, 10–13).

**OGC SensorML 3.0 and OGC/ISO OMS 3.0.** SensorML supports physical-process descriptions that can include component processes and detailed methods; OMS separates an observing procedure from the Observer and the actual Observation. I05/I06/I07's findings provide *possible native description subjects* but do **not justify authoring a method execution, observed result or complete SensorML system instance without data** (Open Geospatial Consortium 2025b, §§ 8.3–8.6; Open Geospatial Consortium and International Organization for Standardization 2023, §§ 8.2, 8.5–8.6).

**IDTA AAS 3.2.** An Asset is not its identifiable Asset Administration Shell, and native `AssetInformation` links them. The AAS rule that one Shell represents one Asset **is scoped to that metamodel**, not a universal rule about how many Smart Citizen records or API resources can concern a physical Kit. An AAS `assetType` type-asset link and CSAPI's `assetType = Equipment` also carry different source meanings (Industrial Digital Twin Association 2026, “Asset Administration Shell Attributes,” “Asset Information Attributes”).

**W3C WoT Architecture and Thing Description 1.1 (Recommendations, 2023).** A Thing can abstract physical **or virtual** entities; a Thing Description specifies Thing metadata/interface, and an Intermediary may publish a proxy representation **with the original identifier or a new one** (World Wide Web Consortium 2023a, § 6.10.2; 2023b, abstract). **No WoT proxy or Thing Description has been documented for this particular Kit**. The standard's proxy model is an interpretive warning against ID equality, not grounds to label the Smart Citizen Platform a WoT proxy.

**OPC UA Part 100: Devices, version 1.05.0.** Native `NodeId` identifies an OPC UA AddressSpace Node; it does not itself certify physical Device identity. The native Online/Offline Device Model and Integration Host Model can expose different views and topology while retaining manufacturer nameplate information. **No OPC UA server or Node instance was examined for SCK2.3** (OPC Foundation n.d., §§ 4.5, 6.1–6.3).

**ETSI SAREF 4.1.1.** A `saref:Service` provides a digital representation of a **Function**, not necessarily a digital duplicate of an entire physical Device. This is a good reason not to promote every Smart Citizen API channel or firmware action into a full-system representation (European Telecommunications Standards Institute 2024, “Services and Operations”).

**OSUS-R pinned implementation.** Its `Asset` and `AssetProxy` are Java software interfaces separating a consumer-facing abstraction and hardware-specific adapter; they corroborate the value of representation boundaries, **but neither is a deployed Smart Citizen API implementation nor a donor-owned generic DIM class** (OSUS-R Contributors 2023, `Asset.java`/`AssetProxy.java` at pinned revision `d09088fbe56d4b64f0544d72e98c3cb70fa941f6`, as recorded in the original [Pass 5](../../DIM_Profile_V2_Canonical_Concept_Pass5_Digital_Representation_and_Proxy_Identity_v0.1_26OCT2026.md)).

**Vocabulary collision to preserve:** In the earlier advanced calibration guide, prose `kit ID` means the **platform page ID**; the pinned backend's older kit-model migrations use database `kit_id` to reference a **Kit type/configuration**. These *cannot* be equated by string matching. Because that migration records a **historical refactor** rather than current deployed API behavior, it is **a caution**, not a new positive identity mapping (Smart Citizen 2026, [guide's kit ID](https://github.com/fablabbcn/smartcitizen-docs/blob/0a18bc0bd372d2bcedfca5bc5e6109f88ea8519f/docs/guides/data/handling-calibration-data.md#L20-L25); Fab Lab Barcelona 2026c, [2023 migration](https://github.com/fablabbcn/smartcitizen-api/blob/25a524cbfb036f8950c247b847d8884a4e776297/db/migrate/20230704150532_refactor_kits.rb#L104-L113)).

It proves that the source distinctions matter to avoid actual misinterpretations, but does **not yet prove** a V2 DIM preserves full information from a serial-specific installation. There is no real counterpart to join all information categories into a single physical individual.

**Genuine remaining needs, not invented profile gaps:** Establish at least one real, traceable device record, source identity/hardware revision, installed PM module and timestamped observations to test positive identity/provenance joins; decide whether a future DIM slice needs explicit source identity and digital representation references or whether that belongs in bindings/provenance; select warranted component granularity and what method information can be sourced rather than imagined. A missing live record is an **evidence gap**, not automatically a semantic gap in CSAPI or donor standards.

## 6. Implications for the next bounded modeling step

**I09 may proceed on a strictly qualified basis**: consolidate the *smallest supported conceptual slice* to express **the distinctions** supported by manufacturer design and donor meanings, with clearly named **unpopulated fields/links** for physical equipment identity, actual methods/results, real replacement events and representation mapping. No actual System instance may be asserted. A vendor-specific software `Component` should **not** be adopted as a physical `Component` class just because both words are identical.

The decisive I09 question is **which candidate concepts/relationships genuinely deserve implementation-independent DIM expression**, versus being left as source-native details or technology-specific **CSAPI/API bindings**. Existing donor concepts should remain first choice; no class, root term, one-to-one representation rule or normative profile requirement has yet earned adoption. **A matrix/textual model view may be more defensible than an invented UML class diagram.**

**PITON B** is the companion, current case-study restart checkpoint [PITON B — Five-Finding Reconciliation and Gate B Continuity](PITON_B_Real_Equipment_DIM_Validation_v0.1_28OCT2026.md). It explicitly supersedes the **progress** portion of PITON A, not its still-valid evidence safeguards.

**Next: I09 — Consolidate a candidate DIM conceptual slice, using only source-supported distinctions from I05–I08 under Gate A/B conditional limits.** Do not begin a complete class hierarchy, XML/JSON schema, final domain name or profile SHALL; stop after the I09 artifact and name I10 next. **Say “proceed” to begin.**
