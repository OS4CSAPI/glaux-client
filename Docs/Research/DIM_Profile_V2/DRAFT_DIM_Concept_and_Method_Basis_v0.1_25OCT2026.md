# Draft Extension to the DIM/Profile V2 Concept Baseline: Domain Information Model Method, Purpose, and Modular Structure

**Working draft v0.1 — 25 October 2026**  
**Status:** Research extension to `DRAFT_Concept_Baseline_v0.1_25OCT2026.md`; not a normative model, profile, or final modular architecture.

## 1. Purpose and relationship to the concept baseline

The initial V2 concept baseline established a disciplined starting point for the thing being modeled: “whole system” means informational completeness about a deployed sensor system, the strongest current top-level characterization is `Sensor + Equipment`, and CSAPI Composition and Aggregation preserve an important distinction between enduring and deployment-scoped subsystem relationships. That baseline intentionally stopped before broader donor synthesis and before defining the methodology by which the Domain Information Model itself should be constructed. This extension records the subsequent research into whether “Domain Information Model” is an established and appropriate modeling approach and what that choice implies for the relationship among the DIM, the intended application profile, future modular structure, and eventual OGC binding. It does not alter the unresolved domain boundary or create a new name for the family of systems under study.

The principal conclusion is that **Domain Information Model (DIM) should be retained as the working name and methodological anchor for V2**. The exact term is used in current ISO/IEEE standardization for an abstract, object-oriented information model of a bounded device-communication domain, while the broader information-modeling practice is well established across IETF, OGC, DMTF, TM Forum, NIEM, and other standards communities (ISO and IEEE 2020; Pras and Schoenwaelder 2003). The V2 use of DIM should nevertheless be explicitly defined rather than treated as a self-explanatory project label. The project should anchor the term in the established practice of domain-scoped, implementation-independent information modeling.

## 2. Working definition of the V2 Domain Information Model

RFC 3444 characterizes an information model as a conceptual representation of a managed environment that is independent of particular implementations and transport protocols and that defines relationships among the modeled objects; multiple lower-level data models may be derived from one information model (Pras and Schoenwaelder 2003, secs. 2–4). OGC similarly describes a conceptual model as an implementation-independent representation of the important concepts of a domain and recommends that OGC conceptual models remain platform independent (Open Geospatial Consortium 2021, secs. 1.3, 3.1). ISO/IEEE 11073-10201 supplies a domain-specific precedent by defining a general object-oriented Domain Information Model for medical-device communication that can support multiple implementation technologies, transfer syntaxes, and application-service models (ISO and IEEE 2020). Together these sources support treating the V2 DIM as a semantic model of a bounded problem domain rather than as a CSAPI schema or implementation design.

For V2, the working definition is: **a Domain Information Model is an implementation- and protocol-independent model of the common concepts, entities, relationships, and intrinsic semantic constraints needed to describe and understand a defined problem domain**. The project-specific purpose is to model the information needed to understand a deployed sensor system as a complete operational subject, independently of the particular API, encoding, schema, software implementation, or user interface used to represent that information. The definition allows concepts, relationships, specialization, identity distinctions, states, lifecycle concepts, activities, temporal or spatial relationships, and genuinely domain-semantic constraints when evidence supports them. It does not make API paths, JSON member placement, SensorML or SWE encoding choices, HTTP behavior, user-interface design, or implementation-specific obligations part of the DIM merely because those concerns eventually realize the model.

## 3. The DIM is purpose-driven but binding-independent

The DIM should not be developed as though the intended CSAPI application profile does not exist. Information-modeling practice commonly begins from real operational or information-exchange needs, and NIEM explicitly instructs domain modelers to map real data requirements to existing components, perform gap analysis, and create new components only when required (NIEM 2016). Likewise, the ISO/IEEE 11073 DIM was created for a concrete interoperability purpose while remaining reusable across different implementation technologies and transfer syntaxes (ISO and IEEE 2020). The intended CSAPI profile may therefore legitimately determine which domain questions V2 must be capable of answering.

The governing V2 principle is **purpose-driven but binding-independent**, or more simply: **model for the profile, not to the profile**. The profile use case may identify what information needs coherent meaning, which distinctions matter operationally, and where semantic gaps prevent interoperability, while the DIM establishes those meanings without encoding them as CSAPI resource paths or representation details. The application profile can later select and constrain the DIM content required for a particular interoperability purpose, and the OGC binding can specify how those selected meanings are represented through CSAPI, SensorML, SWE Common, and related mechanisms. This keeps the known end purpose visible without allowing implementation convenience to determine domain truth.

## 4. Domain boundary is not the same thing as a root concept

The continuing search for a term beyond `System`, `Sensor`, and `Equipment` should remain open because an established boundary-defining concept may yet describe the family of things V2 is trying to model more naturally. However, the existence of a domain does not require that the model have one invented or preselected root class. A domain is first a bounded universe of discourse or problem space; its central or anchor concept is a separate modeling question (Open Geospatial Consortium 2021, sec. 3.1). V2 should therefore distinguish the question “what real-world problem space belongs inside this model?” from “which sourced concept is central in its conceptual structure?”

This distinction protects the research from creating a new umbrella concept merely to make the model visually tidy. Later donor evidence may reveal a recognized concept that accurately gathers the relevant sensing-system concerns, or it may confirm that the model should simply remain centered on Sensor with other concepts related to it. Either result is methodologically acceptable. The DIM can have a coherent domain boundary even if several different sourced concepts participate in that boundary. The current `Sensor + Equipment` characterization should consequently remain evidence about the intended hardware sensing cases rather than be promoted into a newly named root class.

## 5. Modular information models are established practice

Modular organization of a large information model is well established, but standards communities use different structures and terminology. DMTF’s Common Information Model distinguishes a platform-independent Core model, Common models for particular areas, and technology-specific extension schemas, allowing specialized content to build on shared semantics rather than reproduce them (DMTF 2010, sec. 2). TM Forum’s Information Framework partitions its information model into domains and further into Aggregate Business Entities, which it describes as subdomains, based on cohesion among related business entities (TM Forum 2026). NIEM likewise promotes reuse of existing components and creation of new components only where requirements reveal real gaps, supporting model content that can be reused in more than one exchange or community context (NIEM 2016).

These precedents support modularity as a V2 design principle but do not prescribe one specific module taxonomy for this domain. V2 should modularize only where a body of concepts has strong internal semantic cohesion, meaningful relationships of its own, bounded dependencies, and plausible independent reuse. A module should not be created merely because a document section or V1 heading existed, and the term “subdomain” should not be applied until the evidence shows that an information subject actually constitutes a coherent domain partition. The model architecture should be discovered from semantic evidence rather than imposed from presentation structure.

## 6. Standing of the eight V1 information subjects

V1 organized its whole-system problem into eight information subjects: identity/model/technical description; equipment/composition/physical arrangement; sensing capabilities/performance/outputs; deployment/emplacement/location/responsibility; operating configuration/modes/actions; communications/connectivity/access; power sources/operating arrangement; and condition/service/recovery/lifecycle. Those subjects remain valuable requirements evidence because they record the clusters of information that emerged when V1 attempted to describe an employed sensing system comprehensively. They should not, however, be inherited automatically as eight V2 subdomains, modules, or “sub-DIMs.” Their architectural status must be re-evaluated under the V2 evidence-first method.

Different V1 subjects may legitimately resolve to different model structures. Identity, for example, may prove to be cross-cutting core semantics rather than an independently reusable domain, while Power or Communications may prove to contain enough coherent concepts, relationships, terminology, and external standards lineage to justify modular treatment. Deployment may prove to be a reusable relationship pattern that cuts across several modules rather than a subdomain in its own right, and condition, service, recovery, and lifecycle may or may not remain one cohesive area after donor comparison. The eight subjects should therefore be treated as **candidate subject areas to test**, not as the predetermined architecture of V2.

## 7. Criteria for promoting a subject area to a reusable module or subdomain

A candidate subject area should be considered for modular or subdomain treatment only when the research shows more than topical similarity. Relevant evidence includes strong internal semantic cohesion, identifiable concepts and relationships that can be understood substantially independently, meaningful applicability across more than one specialization, bounded dependencies on the rest of the model, and substantial supporting standards or donor lineage. Independent reuse should be a consequence of those characteristics rather than the primary reason for generalizing the model. The eventual visualization and modeling convention should make the distinction among core concepts, modules, specializations, and cross-cutting relationships explicit once those categories are actually earned.

This criterion allows V2 to remain specific to the real systems that motivate the current profile while preserving useful model structure for future work. A coherent Power module, for example, could remain precise about electrical equipment, sources, storage, consumers, interfaces, measurements, and service relationships without being generalized into vague “operational resource” semantics simply to make it apply to unrelated kinds of Sensors. Reusability should preserve meaning rather than dilute it. Where a concept is genuinely invariant across system families, it should be modeled once; where it varies materially by realization or mission, specialization should preserve that difference.

## 8. Reuse policy: reuse invariants and specialize variation

The preferred V2 reuse policy is **reuse invariants; specialize variation**. Common concepts should be common only when their meaning really survives across the relevant system families, and realization-specific concepts should remain specific even when that reduces superficial reuse. This principle is consistent with NIEM’s emphasis on reuse followed by explicit gap analysis and with DMTF’s separation of common model content from extension schemas (NIEM 2016; DMTF 2010). It also protects V2 from the opposite errors of cloning entire models for every sensor family and abstracting the model until it no longer describes any real system precisely.

A possible future Human Sensor profile provides a useful architectural thought experiment but should not become a present modeling requirement. If later evidence shows that Sensor identity, observing procedures, observations, deployment/employment, provenance, responsibility, or other semantics are genuinely shared between Equipment Sensors and Human Sensors, those concepts should be reusable without duplication. Hardware composition, electrical power, equipment interfaces, maintenance, or other realization-specific semantics should not be generalized merely to force them into the same module. V2 should optimize first for semantic correctness of its demonstrated domain and preserve reuse where the semantics themselves justify it.

## 9. Relationship of DIM, profile, binding, and implementation

The DIM and application profile should be understood as complementary artifacts with different responsibilities rather than as independent projects that happen to interact later. The DIM answers what domain concepts and relationships mean; the application profile selects the content and additional interoperability obligations that participating implementations agree to support for a particular purpose. The OGC binding determines how those selected meanings and obligations are expressed using CSAPI, SensorML, SWE Common, and other chosen standards, while implementations produce, consume, validate, manage, and present those representations. RFC 3444’s separation between conceptual information models and lower-level data models provides the fundamental rationale for preserving these layers (Pras and Schoenwaelder 2003, secs. 2–4).

The dependency should therefore run from domain understanding through the DIM into purpose-specific profiles and bindings, even though profile requirements helped motivate the DIM in the first place. In practical terms, **the profile supplies requirements to the DIM, and the DIM supplies semantics to the profile**. A profile requirement may reveal that a concept must be modeled, but it cannot make an API convenience into a domain fact. Conversely, the DIM may contain coherent reusable concepts that a particular profile does not select, preserving the possibility of future profiles or bindings without forcing the current profile to support everything the DIM knows.

## 10. Implications for the current CSAPI-derived findings

The V2 concept baseline’s use of CSAPI `systemType = Sensor` and `assetType = Equipment` remains valuable, but the distinction between semantic source and implementation binding must now be explicit. The domain meanings represented by Sensor and Equipment may become DIM concepts if the controlled source analysis supports them, while the actual CSAPI members `systemType` and `assetType` belong to the OGC binding. The same rule applies to subsystem semantics: the enduring-versus-deployment-scoped distinction revealed by CSAPI Composition and Aggregation may prove to belong in the DIM, whereas the `/subsystems` endpoint, Deployment resources, and link structures are binding mechanisms. V2 should preserve the semantic distinction without conflating the concept with its CSAPI carrier.

This separation also clarifies how CSAPI can legitimately influence an implementation-independent DIM. A base standard may expose a real domain distinction that the model should preserve, just as a donor ontology, engineering model, or operational standard may expose one. Once that distinction enters the DIM, its meaning must be stated independently enough that another binding could theoretically represent the same domain concept differently. The eventual CSAPI profile remains the intended implementation target, but it should be demonstrably a realization of the DIM rather than the source code from which the DIM is reverse-engineered.

## 11. Working decisions and open questions

The table below records what this extension supports as a working decision and what remains deliberately open. “Working decision” means the research is strong enough to control subsequent methodology unless later evidence overturns it; it does not mean the technical content of the eventual DIM has been selected. “Open” means the question should be answered through the controlled donor review and synthesis process rather than by convenience. These distinctions extend rather than replace the standing table in the original concept baseline.

| Topic | Standing | Result |
| --- | --- | --- |
| “Domain Information Model” terminology | Working decision | Retain DIM as an established and appropriate methodological term. |
| DIM abstraction level | Working decision | Domain-scoped, conceptual, implementation- and protocol-independent. |
| Relationship to intended CSAPI profile | Working decision | Purpose-driven but binding-independent: model for the profile, not to the profile. |
| DIM/profile directionality | Working decision | Profile requirements identify needed domain questions; DIM supplies semantics; profile later selects and constrains content. |
| Domain boundary vs root concept | Working decision | Treat as separate questions; do not invent a root umbrella class merely to define the domain. |
| Modular architecture | Working decision | Permit and prefer modularity where semantic cohesion and reuse are demonstrated. |
| V1 eight information subjects | Candidate evidence | Treat as candidate subject areas, not inherited subdomains or sub-DIMs. |
| “Subdomain” terminology | Open | Apply only where evidence demonstrates a coherent domain partition. |
| Core/common content | Open | Identify through cross-source synthesis rather than declare in advance. |
| Reusable modules | Open | Derive from semantic cohesion, bounded dependencies, source lineage, and demonstrated applicability. |
| Future Sensor realizations | Architectural test only | Do not generalize current semantics merely to accommodate hypothetical Human, Simulation, or other profiles. |
| Final domain-family name | Open | Continue searching for an established boundary-defining concept; do not coin one prematurely. |
| Final DIM content | Open | No donor extraction or synthesis decision has yet populated the V2 DIM. |

## 12. Research gate and next methodological step

This extension strengthens the basis for continuing Workstream 1 but does not itself complete the whole V2 research program. Before construction of the DIM begins, the project should preserve these methodological decisions as the governing basis for later donor review: the DIM is purpose-driven but binding-independent, domain boundary and root concept are distinct, modularity follows semantic cohesion, and the V1 subject areas are hypotheses to test rather than architecture to inherit. The donor process should then be able to ask not only whether a source contributes a concept, but whether it reveals core semantics, a coherent reusable module, a specialization, a cross-cutting relationship, or evidence that an apparent V1 grouping should be dissolved. No new model content should be adopted merely because this methodological structure makes a place available for it.

The immediate remaining Workstream 1 task is therefore not to populate modules, but to decide whether this Concept and Method Basis is sufficiently complete to close the methodological grounding phase. If accepted, Workstream 2 can establish the controlled visual/modeling notation that will represent the DIM, its modules, source distinctions, and evidence without introducing new semantics through diagram design. Workstream 3 can then organize the neutral donor population and establish the common extraction and disposition method before substantive synthesis begins. The order remains deliberate because modeling notation and donor grouping should operate on a settled methodological foundation rather than help define it accidentally.
