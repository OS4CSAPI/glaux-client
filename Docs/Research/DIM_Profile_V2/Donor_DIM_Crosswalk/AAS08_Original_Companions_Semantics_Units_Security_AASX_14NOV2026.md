# AAS08 — Original companion specifications: semantics, units, security and AASX

14 November 2026 · research/dim-profile-v2 · preflight `ff031b647f218e0782294f38ff6bbed691800bba` · owner-authorized AAS08 only.

The Asset Administration Shell (AAS) companions add precision about what a concept means, which quantity and unit a value uses, how access policy is described, and how files are exchanged. These are different subjects: a concept definition is not a measurement, a rule is not an observed authorization decision, and a package is not an assembly of equipment. The Domain Information Model (DIM) and OGC API – Connected Systems (CSAPI) Profile remain undecided; AAS stays active and source-incomplete.

## What the sources establish

Part3a supplies a dictionary-style definition of a property or coded value, including names, meaning, datatype and units. Its optional class fields are constrained by explicit rules, including English names/definitions and units for quantitative datatypes; the legacy category tables do not override those rules. Part3b adds a separate unit definition, quantity and dictionary/version context and specifically cautions that equal units do not mean equal quantities. This supports more faithful interpretation of existing sensor values without inventing a sensor-observable catalogue or automatic unit-conversion behavior.

Part4 separates authenticated claims, access-rule descriptions, policy decisions and enforcement. A VIEW permission can reveal existence without values, filters can hide fragments, and the receiving security domain must establish its own policy. The specification itself says identifier-to-asset binding is unprotected and discusses stronger identities as possible approaches. Its requirements, JWT syntax, audit guidance and examples do not establish that a live system securely identifies or controls the equipment.

Part5 defines a container for selected AAS information and supplementary files, with relationships, serialization conventions and signing/encryption guidance. Its package metadata describes the package and its physical ZIP layout describes files. Neither proves physical composition, original event lineage or a complete installation record; storing a package through Part2 does not validate it. The inspected sample and contradictory source statements remain evidence with limitations, not a certified implementation.
