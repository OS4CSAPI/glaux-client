## Retained architecture meanings and corrections

ISA is described as a software-only interoperability solution relying on platform networking, computing and synchronized authoritative time. That statement does not make every represented member software or equate a component with one operating-system process. GPS is an example of a time source, not a universal required device, accuracy specification or traceability claim. Capability declarations indicate support; they do not prove current readiness, permission, execution or physical effect.

Every ISA component supports initiating a connection to a Controller, including Controllers. Controllers additionally accept connections from components and other Controllers. Initiator and non-initiator determine client/server roles for a particular connection; Client and Controller must not become disjoint physical classes. The Introductory Guide’s one-Controller local instance can interconnect into the broader virtual network. A deployment may contain one or many Controllers; tactical placement is a source **should/by-default** recommendation, not an inferred universal physical hierarchy or mandatory full mesh.

An ISA composition is an integration collection exposed through a single CIC, which may but need not be a Controller. Members can be ISA-compliant or use native interfaces. Composition capabilities can combine CIC/member capabilities as well as expose individual capabilities. **Composition does not by itself establish a physical assembly; membership does not prove physical part-of; an interface does not prove a cable or external-equipment arrangement.** Original rows S06-R005–008 now state these qualifications. The preserved delivery 14 entry in `completed_batch_history` stores exact before/after values and source reasons; all other donor/case columns remain unchanged.

The CIC determines network exposure and attribution. A visible member is announced, has declared capabilities and periodic status, and is represented as the origin of its communicated information. An opaque member is not announced; its exposed capabilities are represented as CIC-provided. A non-ISA member made visible is a virtual ISA component. The member identifier includes the CIC identifier, but this does not introduce a new serialization rule or prove physical containment; retain earlier UCI evidence. This architecture sense of visibility is distinct from the DMS laser Visible property.

Only visible members can be targeted externally. The SDD calls visible/taskable members transparent and visible/untaskable members translucent. Figure 2 labels B as translucent but includes “Member B tasks” on an incoming network-to-CIC arrow; only C has a forwarding task arrow. Preserve this tension without making B taskable or deleting a source label. For a particular request, CIC can be performer, broker or relay; these responsibilities are not hardware classes or execution results.

ISA 6.0 Controllers must support all three core services; activation is separate. Section 5.0’s typical hosting statements and Figure 3 remain distinct from the support rule. Optional services may be supplied by any component, with **should** guidance to declare their defined capabilities; the DMS provider-support descriptions retain **must**. The six saved DMS service command lists remain unchanged. Neither future remote service-placement ideas nor possible future relaxation of Controller constraints are current 6.0 behavior.

Controller endpoint discovery uses local configuration or source-described Zeroconf/mDNS discovery. It is distinct from the DMS Discover query for current message/component information. Connection establishment uses source-listed IPv4/IPv6, TCP and TLS; presentation negotiation separates message encoding from data-model schema version. Protocol Buffers and XML are named encodings, and IPL handles negotiation/exchange. Delivery 15 now supplies the separately attributed ICD connection, TLS 1.2, format-pair, framing and certificate guidance described above. No deployed configuration or tested security result is inferred.

The participation lifecycle has six phases: Connection, Registration, Configuration, Operational, Deregistration, Disconnection. Table 5 starts Configuration with sending initial Config and places entry to Operational at receipt of the Controller’s initial Config; Figure 5 uses that received-Config transition, while Figure 16 reaches its Operational endpoint after receipt of initial Status. Preserve both source timings without inventing their reconciliation. Operational requires periodic Status; registration renewal uses RENEW and the registration flow, while nonresponsive/revived handling has a separate Status-based path. Deregistration and connection termination differ; a connection may remain open, and none of these phases establishes equipment health, physical asset lifecycle or command status.

Status is also a heartbeat; absence of a report establishes no physical failure. Initial status, periodic changes, unchanged heartbeats, readiness/reporting selection and explicit Get Status selection retain their distinctions. Initial-Status timer prose and figure annotations differ, and one missed-status paragraph says renewal while its figure shows nonresponsive/revival handling. These are local source notes, not fabricated implementation choices or extra deliveries.
