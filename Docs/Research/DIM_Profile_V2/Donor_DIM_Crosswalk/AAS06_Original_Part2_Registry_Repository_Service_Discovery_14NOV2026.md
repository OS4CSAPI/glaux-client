**One owner-authorized AAS06 scope only.** The purpose is to understand original API-native service roles and selected operation, representation, lookup and profile contracts for a whole-sensing-system comparison. ## What we have learned

The original architecture separates **Discovery**, **Registry**, **Repository**, and **AAS Service**. Discovery matches asset identifiers or links to one or more shell identifiers; a registry records descriptors pointing to API endpoints; a repository manages digital AAS records; a standalone AAS service provides the interface of one shell. A descriptor is not the physical equipment and can omit its own endpoint while pointing to Submodel endpoints, and the native text says the AAS record is source of truth when a descriptor disagrees. This gives a conditional **client navigation pattern**, not an adopted cross-standard requirement or proof of a manufacturer device connection.

Service profiles are separately versioned capabilities. Registry has full, read, bulk, query and minimal-read profiles; Repository has full, read, query, signature, identifiable and history; standalone Service has full and read; Discovery has full and read. A server's `/description` advertises a bounded list of profiles that apply at that API path and its children. A read profile may use an HTTP POST for read-only search; a documented profile does not prove an operation was called, allowed or effective on real sensing equipment.

Three **source contradictions/ceilings** have to remain visible. Discovery SSP-002 is called a Read profile and declares pagination unsupported in the publication text, yet pinned OpenAPI specifies `Limit`, `Cursor` and `PagedResult`. The ServiceDescription description requires one or more declared profiles, while the shared OpenAPI array has `minItems: 1` but does not mark `profiles` as a required property. The Registry Query SSP-004 profile is mislabeled “Bulk” in a presentation field despite its Query identifier and actual POST query contract; a direct-ID-Link LinkSet illustration also contains non-matching example profile references. None licenses fixing the publisher on the owner's behalf.

Time and trust boundaries matter. The Repository History profile's `GetAssetAdministrationShellVersionByIdAndDate` retrieves an AAS record as of a date, but the normative original note explicitly distinguishes this history from `AdministrativeInformation.version`; the source does not prescribe what every change must do to historical versions. The separate RecentChanges operation is marked *Experimental*, and a JWS-returning Signature profile establishes neither signer verification nor original manufacturer or NOAA truth. Generic HTTP 200/202 or 401/403 status codes are API-level results, not a physical Command acknowledgment or an authenticated source assertion.

Finally, identifiers and formats must retain native meaning. An Asset-ID is not an AAS-ID; HTTP path identifiers are base64url encoded; `idShortPath` addresses nested model elements; cursor values are opaque; and the `api/v3` URL prefix is merely recommended/example, not guaranteed. Full versus read/query/history profiles and Normal versus Value/Metadata representations differ. They are plausible **optional information and navigation needs** for a common Details view but do not force new DIM fields/classes, universally mandatory CSAPI paths, or a sensor/equipment chassis.
