## Why each new information need was added

“Common” means potentially useful across equipment domains, not mandatory for all equipment. “Specialized” retains a particular architecture or engineering practice. The table records the distinct subject/role that justified each candidate; exact original locators and later qualifications remain in the canonical row and stage ledger.

| Candidate and stable row ID | Class | Reason for a separate candidate |
|---|---|---|
| Digital-record identity and contextual element identification (`AAS-O2-RECORD-ID`) | Common | The existing persistent System identifier row qualifies asset identity but does not separately represent the identity of its digital records and their locally referenced elements. |
| Digital-record administration and business revision (`AAS-O2-RECORD-ADMIN`) | Common | Configuration version concerns equipment settings; source-qualified assertion concerns evidence attribution. Neither existing row explicitly carries the digital record lifecycle and revision context. |
| Template that guided creation of a digital record (`AAS-O2-TEMPLATE-PROVENANCE`) | Common | A structure declaration describes a reusable shape; this candidate records which template guided a particular creation. A generic source assertion does not expose that distinct relationship. |
| Applied supplementary data-specification templates (`AAS-O2-DATA-SPEC`) | Specialized | Existing custom-structure/property-declaration rows do not explicitly identify the supplementary specification applied to an element. Retain this AAS mechanism as an optional specialization; companion contents remain bounded. |
| Identified information aspect and contained elements (`AAS-O2-ASPECT-GROUP`) | Common | The described-system and physical-constituent rows concern the represented subject; a reusable custom-type declaration is not the identified information aspect itself. |
| Semantically defined relationship and its annotations (`AAS-O2-LOGICAL-RELATION`) | Common | The existing rows describe particular physical or observation relationships. They do not represent a general declared relationship with its own meaning and qualifying annotations. |
| Multilingual display label and description of an information element (`AAS-O2-ELEMENT-LABEL`) | Common | The existing changeable equipment-name row has a different subject. Display text for arbitrary information elements needs its own qualified candidate. |
| Supporting file locator or embedded file content (`AAS-O2-SUPPORTING-CONTENT`) | Common | Existing media rows are specifically observation-associated or component-generated. The native file/content mechanisms also support general descriptive material and must not be forced into those narrower subjects. |
| Event declaration, direction and on/off state (`AAS-O3-EVENT-DECLARATION`) | Specialized | The existing rows concern observations, equipment condition or capability readiness. None names the declared event mechanism and its own state; retain this source-specific architecture detail together rather than creating one row per attribute. |
| Event message source and logical scope (`AAS-O3-EVENT-SOURCE-SCOPE`) | Common | A source event declaration and affected logical scope are distinct information from occurrence identity, detector snapshots and generic relationship links. Preserve those narrower holds while exposing the positive source meaning. |
| Event communication topic and broker reference (`AAS-O3-EVENT-ROUTING`) | Specialized | Channel and broker-description references are not exchange participants or an installed network path. Keep this optional messaging-architecture detail visible without adopting a universal transport contract. |
| Attributed initiator of event creation (`AAS-O3-EVENT-INITIATOR`) | Common | The initiating subject may differ from a message author, sender or record creator. A separately qualified attribution candidate preserves this role without weakening the existing evidence/provenance holds. |
| Value, concept and template qualification (`AAS-O3-QUALIFIED-CONTEXT`) | Common | Context about how a value or concept should be interpreted is broader than equipment condition or qualitative output quality. Retain one qualified-context need without promoting example values or native kind literals into adopted DIM fields. |
| Digital-record discovery and service-location association (`AAS-O4-RECORD-LOOKUP`) | Common | Record identity names a record, and participant/connection rows describe endpoints. | Digital-record state at a specified time (`AAS-O4-RECORD-HISTORY`) | Common | A business revision label does not identify the record content valid at a requested time. Operating-state and equipment-service histories concern different subjects. Preserve one optional common temporal-record need, with source-specific History profile and experimental recent-change limitations; do not infer equipment history. |
| Client-suggested operation timeout (`AAS-O5-OPERATION-TIMEOUT`) | Common | Existing execution and request-correlation rows describe progress and identity, while message validity concerns data expiry. None explicitly carries the client-suggested execution time budget. Retain a common optional information need, not a server-enforced deadline or universal Profile requirement. |
| Exchange-package identity and associated digital records (`AAS-O5-PACKAGE-ASSOCIATION`) | Specialized | A supporting file row does not identify a managed exchange package or its declared record associations. | Unit definition and quantity context (`AAS-O6-UNIT-CONTEXT`) | Common | Existing property/observable rows identify what a value means; the measurement row remains held for uncertainty. Neither carries the separate unit concept and its applicable quantity/dictionary context. Retain one optional common candidate, without inventing separate mandatory fields for each native attribute. |
| Access-rule definition and protected information (`AAS-O6-ACCESS-RULE`) | Common | Request-access metadata carries credentials/claims, permission-decision rows report decisions, and filtering describes selected output. None explicitly represents the reusable rule that relates protected objects, rights and conditions. This is a separate information need, not an extra row for every temporal value. |

## Why the other findings did not become new rows

An original attribute is not automatically a new information need. Many findings refine subjects already represented by product identity, physical structure, property/operation declarations, assertions or earlier new candidates. Other findings describe serialization, query/pagination, native cardinality, profile selection or package-validation mechanics; their evidence remains available without inventing a field for each mechanism. Examples, future features, unresolved source contradictions and unread external specifications do not establish additional equipment facts.

The current AAS column has **88 source-bearing comparisons**: 57 common candidates, 14 specialized candidates, two native-only evidence entries, three unresolved candidates and 12 held comparisons. These include previously existing comparisons and the 24 additions; they are not 88 newly discovered fields. The other 273 rows remain explicit: 264 have no established AAS comparison and nine retain source-case holds. Neither category asserts that AAS lacks an equivalent.
