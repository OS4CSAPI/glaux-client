## 1. Purpose and the specific failure being corrected

The owner reasonably read an empty ISA cell as a possible absence of the corresponding concept. Direct inspection then found native `Manufacturer`, `Model`, and `Serial Number` properties in the ISA Data Model Specification (DMS), release 6.0 revision 12, printed pages 13, 14 and 16 (PDF pages 28, 29 and 31). The prior eleven-record ISA selection had omitted them. Existing workbook consistency checks could not detect concepts that never entered the selection.

The old plan already allowed more than one pass per donor and said blanks did not establish absence. The execution mistake was selecting a small set of interesting concepts and closing the donor pass without accounting for the rest. The planning weakness was the lack of an enforceable source-entry inventory and row-coverage requirement. Neither issue is solved by adding three cells alone.

**The correction has two directions:** inspect ISA against every current proposed Domain Information Model (DIM) row, and inspect ISA's own source inventory for relevant concepts that need additional rows or distinct relationships. Existing donor-verified content is retained unless a particular source comparison establishes a specific correction.

## 3. Source boundary: establish it from the corpus, not from the old selection

Primary defining sources are the 31 October 2023 ISA 6.0 originals: DMS revision 12; Software Design Document (SDD) revision 5; Interface Control Document (ICD) revision 5; Component Requirements revision 4; Controller Requirements revision 4. Review the full DMS conceptual inventory, including its services, capability bins, properties, observables, commands, message and data-type definitions, field structures, and relevant enumerations/constraints. The DMS table of contents and body headings provide a source-native checklist independent of the old crosswalk.

ISA-01 must also account for the other ISA documents already in the donor register: Data Model Topics r2, Data Query Language User's Guide r4, Introductory Guide r2, White Paper r2, Certificate Usage Guide r2 and IPL3 Usage Guide r4, plus the historical 2015 architecture paper. Verify editions/access rather than assuming them from these labels. Assign their potentially distinct conceptual content to the appropriate pass. Sources used only as context or implementation detail receive a specific reason; they do not disappear from the register. No new unrestricted literature campaign is authorized.

Use the original project PDFs through Files. A failed raw-byte export is not a finding that the text is unavailable. Search by exact title and revision if an old file handle no longer resolves. Read full definitions and referenced types, not only matching search snippets or an earlier AI report. Inspect page images when table layout, extension marks or figures affect interpretation. Record exact source title, edition, section, printed page and PDF page; do not pretend a repository summary is the original standard.

Distinguish core entries from Custom, Nominated and Accepted extensions using the original DMS legend and body entries. A symbol in a table of contents is not, by itself, an adequate source-status decision. Keep capability declaration, current state, physical identity, network role, observation report, actual act and command outcome separate.

## 5. What a cell and a source entry must say

Keep **review coverage**, **mapping relationship** and **model acceptance** as separate fields. A reviewed PARTIAL mapping is not unreviewed; a fully reviewed candidate row can await the owner's model decision without invalidating the source review.

In the ISA review display, a populated cell contains the actual source-native term. An otherwise empty position must be intelligible: `Not reviewed`, `Question [ID]`, or `No correspondence found in [named scope]`. Use a compact marker and linked legend if necessary; do not bury the distinction in a disclaimer elsewhere. Do not infer “ISA cannot represent this” from a scoped no-correspondence result.

Every source inventory entry receives one of these dispositions: mapped to existing row(s); represented by a candidate new/split row; supporting definition referenced by mapped content; duplicate/alias with canonical entry; outside this model target with a specific reason; or a specific open source/meaning question. Preserve parent/child and field/type dependencies. Multiple source fields may support one row, and one source concept may inform several rows; retain their individual evidence links.

`Not reviewed` is a work state, never a semantic conclusion. `Question` must identify what is uncertain, the affected record, the source already examined and the next resolving action. Do not use outside-scope or duplicate labels as a way to avoid a difficult source comparison.

## 6. Evidence and anti-hallucination checks

For each added or revised mapping, store the actual ISA term and type (property, field, message, architectural role, association, command or type), exact original locator, brief meaning, subject scope, source/extension standing, relation to the proposed DIM element and the particular difference that matters. Where a field is defined through another type, follow that type before asserting a meaning. Requirements, descriptive prose and examples remain distinguishable.

Before each substantive pass, read the current plan/progress, the source pages assigned to that pass and the relevant current rows. Afterward, save the evidence and visible workbook/view changes, list source entries handled and the exact remaining queue, then read back the published files. Reuse the existing generation/checking machinery where suitable; do not turn each correction pass into a new software-building exercise. Preserve old source entries unless the revision explains why they changed.

The four equipment cases are useful falsification checks, not a restriction that only concepts they exhibit are relevant. Preserve reference design versus installed unit, physical module versus reported quantity, logger state versus environmental measurement, original event versus digital copy, and known versus inferred historical data. Do not synthesize unavailable case values to fill a display.

Automated tests must check source-inventory coverage as well as file consistency: all registered entries assigned/dispositioned, all original 22 plus nine row targets accounted for, all former eleven mappings and fourteen holds reconciled, evidence/worksheet parity, and non-ISA content unchanged. A fresh semantic pass must still compare interpretations with original wording. A generated ledger checked only against itself is insufficient evidence of source coverage.

## 7. Completion and wording contract

The ISA correction is complete when:

1. The agreed ISA source inventory has been traversed and reconciled with the original contents/body/index; every entry has an explicit, justified disposition and all referenced semantic dependencies have been handled.
2. All 22 existing DIM rows and nine case-review topics have an ISA coverage outcome; the Manufacturer, Model and Serial Number omissions are corrected; the original eleven mappings and fourteen holds have been reconciled.
3. Relevant unique ISA concepts have visible, traceable candidate rows or explicit design decisions instead of disappearing because the old table lacked a row.
4. No unreviewed or unassigned work remains in the agreed scope. A specific unresolved interpretation may be a completed review outcome if the sources, exact alternatives and affected mapping are recorded and no unsupported match is asserted. Missing required source inspection is not reclassified as such an interpretation.
5. The source-first audit, workbook/evidence consistency, visual inspection and GitHub readback pass, with the revised ISA view ready for the owner's substantive judgment.

**Use completion statements that mean what they say.** Write “ISA-03 COMPLETE: every property in the assigned block has a recorded disposition; next ISA-04,” when that test passes. At final closeout write “ISA correction COMPLETE,” and list any specific owner decisions separately. Do not append a blanket “not a finished model” caveat that a later chat may mistake for a command to reopen finished work.

A narrow unknown attaches only to its named record and action. A later source discovery may justify changing that record, but an old warning or model-acceptance status alone cannot cancel completed source work. An inaccessible unrelated implementation detail does not become a blocker for the conceptual crosswalk. Equally, do not claim an unread section was examined merely to use the word complete.
