## 1. Purpose, fit and hard boundaries

The project seeks one source-grounded, whole-sensing-system Domain Information Model (DIM) and an Open Geospatial Consortium (OGC) API – Connected Systems (CSAPI) Profile that can support a coherent cross-vendor client Details view without erasing equipment-specific facts. AAS is an industrial digital-twin/information-model donor, **not** an assumed sensor chassis, an OGC-native API, or a source proving equipment was installed or commands executed. The actual future review must distinguish the AAS information representation from the represented asset; asset kind from identifiable shell; reusable product kind from particular unit; submodel type/template from a populated instance; relationships from physical containment; declared possibilities from observed equipment state; and model/API semantics from source-event evidence. These are **questions to test**, not AAS equivalence findings or adopted modeling decisions.

The existing 40-step donor plan calls Step20 "Asset Administration Shell v3.2: Asset vs Shell, type vs instance and contextual submodels/relationships without mandatory AAS multiplicity inheritance." Treat that old single-line entry as routing, not as evidence that one brief review could cover the publisher corpus. Retain the ISA, The Open Group SOSA C239 (not W3C SOSA/SSN), and SAPIENT original-source rigor, source-specific holds, fair native-first candidate opportunity, and user control: **one separately authorized Proceed = one bounded step, with a named stop**.

## 3. Proposed source-item/section coverage ledger and comparison method

On the **first separately authorized research step**, build or extend the **one cumulative AAS donor original-source/coverage register in the existing Donor_DIM_Crosswalk location**, not an isolated alternative master. Stable IDs must distinguish **publisher release artifact (AAS-C01..C06)**, **native section/figure/table/rule**, **schema file and native path**, and **API service profile/operation**; an example scheme is AAS-C01-S###, AAS-C01-SCHEMA-###, AAS-C02-SVC-###, and AAS-C02-SSP-###, assigned only after actual enumeration. Preserve publisher, edition, source URL/tag/commit, exact locator, object kind and status, normative standing (**Rule / Recommendation / Permission / Observation / definition / example / future / implementation detail**), original source description, and crosswalk evidence grade.

For **every relevant source item/section** use explicit source-contact status: **FULLY READ**, **SAMPLED**, **UNREAD**, **INACCESSIBLE** with exact reason, **IRRELEVANT** with reason, or **UNRESOLVED**. An AAS index, normative reference, tag, repository listing, or schema filename does **not** establish that its original clauses/definitions were inspected. Record actual native counted units separately (sections, fields, operations, constraints, files), not comparable donor-wide "richness" scores or artificially matched iterations.

For each audited native concept, contrast original meaning against existing stable master rows and four real-source situations (Dragino, AirGradient, Campbell/ClimaVue, Bennett). Relations stay **EXACT / PARTIAL / BROADER / NARROWER / RELATED / CONFLICT / NO_ESTABLISHED / UNREVIEWED** with source IDs and original standing. Distinguish common **information need**, industrial-specialized extension candidate, native wire/schema-only evidence, and unresolved meaning using existing source-based color statuses; no row-per-field or adopted class per AAS label. AAS type-instance, cardinality, shell-assets, Submodel or Service semantics must not automatically become universal DIM or OGC CSAPI Profile rules.

**Test questions for later source inspection, not pre-established findings:**
- Is the identified original object a physical asset, logical asset, product kind, individually installed equipment, AAS record, Submodel, SubmodelElement, ConceptDescription, model template or actual API representation?
- Which source-supported identifiers and references represent manufacturer/model, a particular asset, shell and owner, and which relationships are merely information links rather than installed physical composition?
- What originally sourced claims concern properties, capabilities, status, event/time, location, maintenance, versions, files, operations, controls, access/security, unit/semantic references, and what remains absent or unevaluated?
- Which AAS/JSON/REST behaviors can be meaningfully crosswalked with OGC CSAPI System/Procedure/Observation/DataStream/Command and SensorML roles, and which must remain native-specific or "no established equivalent" rather than fabricated interoperable bindings?
- Do the original four equipment/source cases justify a shared Details-view datum, a vendor-specific optional section, only a native attachment, or an explicit UNKNOWN? No device control or real-operation evidence can be inferred from AAS metadata alone.
