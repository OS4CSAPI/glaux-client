## What the architecture review changes

An ISA composition is an integration collection exposed through one **composition interface component (CIC)**. Membership does not by itself establish physical part-of, and an ISA/native member interface does not establish a cable, connector or physical arrangement. The earlier arrangement, participant, constituent and external-equipment ISA cells now state these limits. Their earlier wording and the exact changes remain in the evidence revision audit.

The CIC can make a member visible or opaque. A visible member is announced, has declared capabilities and periodic status, and retains member attribution in communicated information. An opaque member can still contribute exposed capabilities, represented as CIC-provided. A non-ISA member made visible is a **virtual ISA component**; this is distinct from an ISA-compliant member and does not imply a virtual machine or physical containment. SDD 4.2.2 and Figures 32–34 support the exposure/attribution pattern.

For a visible member, external taskability is separate. The SDD calls a taskable visible member **transparent** and an untaskable visible member **translucent**. Figure 2 retains an incoming “Member B tasks” label despite B being translucent; only C has a forwarded task arrow. The review preserves both the definition and diagram without inventing a resolved behavior. For a particular task, the CIC may be performer, broker or relay; these are responsibilities, not equipment classes or proof of execution.

Every ISA component, including a Controller, supports the client-side connection role. Controllers also support the server side; initiator and non-initiator determine the roles for a particular connection. The earlier Introductory Guide local instance remains a one-Controller context that can interconnect with other instances; it is not a global one-Controller limit. The SDD’s virtual network uses existing physical networks, while Controller deployment and interconnection remain distinct from physical equipment hierarchy.

The six participation phases are **Connection, Registration, Configuration, Operational, Deregistration and Disconnection**. They concern one Controller connection, not asset life or physical health. Periodic Status supports availability monitoring; a missed report does not prove failed equipment. Registration renewal, nonresponsive/revived handling, leaving the network and terminating the connection remain distinct. The source allows a connection to remain open after departure.

Presentation negotiation separates **encoding technology from data-model schema version**. The SDD lists Protocol Buffers/XML and IPv4/IPv6, TCP and TLS; IPL negotiates presentation and carries ISA messages. These are source-described architectural choices, not tested settings or security guarantees for a deployment. ICD, certificate and IPL3 detail is the next assigned delivery.

## Reconciliation with completed evidence

Each ISA 6.0 Controller must support the three core services, while support and activation differ. The SDD separately discusses typical hosting; any component may provide optional services. Those statements do not alter the six DMS service definitions or their command lists. Optional-service declaration guidance retains “should,” while DMS provider-support language retains “must.”

The message table is a key-field summary, not a replacement schema. Config declarations/states, Status property values, Event observations, Request invocation, Response disposition and Administrative notifications retain their different meanings. Full DMS fields, required/optional rules, list cardinalities, identity roles and enum codes remain intact. Live Data’s initial-state description retains the DQL `without cache`, projection, matching/context and non-cached Event qualifications.

The 28 detailed flow scenarios are illustrative and explicitly omit message details. The evidence records generic `Authorize` versus the two DMS authorization commands, `script`/`ucis` versus Discover’s full parameter/result names, renewal-versus-revival wording, initial-Status timer wording, SER versus Event Reference, and removal field-label differences. None becomes an invented alias or silent source correction. Observation update affects the referenced observables that are updated; recall advises ceasing use of all observables from the referenced Event, without proving deletion or recipient compliance. Command acknowledgements, progress, completion and physical effects remain separate.

Design qualities, future-release ideas and security/performance statements remain attributed claims in the 2023 source. They do not establish runtime behavior, conformance, measured performance or current security. Source coverage, correct correspondence and owner adoption remain separate decisions.

**Excel snapshot:** the verified 26-sheet workbook remains **253 rows/226 primary outcomes**. Current Markdown/CSV/JSON now contain **325 rows and 480 catalogue outcomes**, 72 rows beyond that snapshot, plus the documented ISA-cell and pattern qualifications. No workbook rebuild was added to this source delivery; retain the existing substantial/final checkpoint cadence.
