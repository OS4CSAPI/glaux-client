# AAS07 — Original Part 2 Submodel, ConceptDescription, and AASX interfaces

14 November 2026 · Branch `research/dim-profile-v2` · Preflight `dde085ecffa47c6dbd833b77ca3983d81036b2e6` · Industrial Digital Twin Association (IDTA) Release 26-01, Part2 APIs 3.2.0, [original pinned source](https://github.com/admin-shell-io/aas-specs-api/tree/f136ba1465e4c6b5b25444e0609d4de8f7429044).

**One owner-authorized source-first AAS07 step.** This is a bounded audit of relevant native meanings, selected original API clauses and the remaining five service families, not a normative all-operation, runtime conformance or Domain Information Model (DIM)/Connected Systems API (CSAPI) Profile approval.

## Principal findings

The native **Submodel Registry describes endpoints**, Submodel Repository stores digital Submodels, standalone Submodel Service provides access/invocation for one Submodel, and ConceptDescription Repository stores semantic description records. None is necessarily a physically installed sensing system, a performed observation, or agreed domain vocabulary. The original Part 2 **AASa-003 and AASa-004** constraints prohibit Template Repository profiles SSP003/004 from accepting/providing `kind=Instance` submodels, so templates cannot be treated as installed objects.

The standalone Submodel Service **Value SSP003** profile includes synchronous `POST /invoke`, so it is *not* simply a read-only profile. An HTTP 202 Accepted response to asynchronous invocation does not establish a valid or successful action; the original source allows later errors, and HTTP 200 may contain `executionState=Failed`. The API has explicit request/result and lifecycle shapes, but nothing inspected here authenticates an actual sensor-command effect.

The AASX File Server may store a package binary and associated shell identifiers without parsing the archive, and stored package does not thereby instantiate an AAS or Submodel. File Server Full and Async profile contracts differ. Source discrepancies remain: Submodel Repository Read SSP002 profile text names the wrong ServiceSpecification; Submodel Registry Query SSP004's Name says Bulk; AASX Async profile describes `InvokeOperationAsync` but its YAML names `PostAsyncAASXPackage`; AASX Async result types also differ between text and YAML. The source says AASX upload is only asynchronous despite the separate Full profile's POST/PUT archive operations; no silent publisher correction is authorized.
