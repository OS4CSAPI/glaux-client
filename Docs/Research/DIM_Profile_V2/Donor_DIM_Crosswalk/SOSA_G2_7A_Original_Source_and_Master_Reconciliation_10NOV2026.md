## 2. Native definitions and edition-specific meaning

**AMPS / AMPS String / ANS / Protocol Field / Protocol Modifier are five different source referents.** Alternate Module Profile Scheme (AMPS) supplies a hardware Plug-In Card Profile (PICP) specification method using a string of protocol fields instead of enumerating every module-profile combination in separate tables. An **AMPS String** is the ordered collection that specifies the physical module-profile design; the **Alternate Naming Structure (ANS)** identifies the associated slot profile without its dash option and the sequence of corresponding port protocol fields. A **Protocol Field** assigns one or more physical-port protocols, while a **Protocol Modifier** adds characters to qualify its protocol; §13.3.1 only defines these concepts and does not provide full later syntax rules.

**The original §13.3.2 explanation has edition-scoped, primarily descriptive source standing.** C239 explains that optical and RF additions produced a combinatorial explosion in traditional ANSI/VITA module-profile dash variants. It describes the early 2020 subcommittee transition to AMPS, an AMPS string as specifying a module profile and hardware features, and the conventional-versus-ANS example in Table13.3.2-1. C239's wording that its PICPs **will** use AMPS is not an original numbered Rule/SHALL within §§13.3.1–13.3.2; it must not silently become a universal CSAPI Profile SHALL or an applied equipment capability.

**The original example is an example, not an installed device.** The table contrasts conventional `MOD3-PAY` / `MOD3p-PAY` expressions with `MODA3-16.6.13-1`, assigning Data/Expansion/Control and optical/coax port groups. The original source distinguishes the ANS slot reference from dash-option loading and allows Expansion lane groups to change granularity. This is not a general DIM topology/physical installation, vendor-provided hardware serial, tested interface, or a realized SensorML physical-system aggregate.
