# RFC 8348 donor review

## Purpose and starting point

Rank 5 in the [existing research order](Donor_Research_Priority_Order.md) and artifact 133 in the [source register](../Donor_Alignment/03_Source_Accountability_Register.csv) address hardware inventory and component relationships. The review asks what a Connected Systems client can learn about physical equipment from a server that implements this model. Start from the accepted [574-row master](https://github.com/OS4CSAPI/glaux-client/blob/2188f1102ed8662b6da225a2ab983b099ead39d6/Docs/Research/DIM_Profile_V2/Donor_DIM_Crosswalk/Master_Donor_Concept_to_DIM_Crosswalk.xlsx). Compare alongside OSUS-R, Redfish, OPC UA Devices and the other researched donors. Final column order and adoption of candidate concepts have separate owner decisions.

## Source intake completed

The March 2018 Standards Track publication describes hardware managed by one server. The [source inventory](RFC_8348_Source_Coverage.json) identifies the dated document, original-text fingerprint, errata search and declarations in three embedded modules. Section 7.1 contains the principal equipment model. Section 7.2 supplies the initial hardware class vocabulary. Appendix A provides a non-normative, temporary state-only model for implementations lacking the newer datastore architecture. Track duplication across the modules. Sections 4–6 describe the relationship to the Entity, Sensor and State Management Information Bases (MIBs). For a cross-reference that changes the meaning of a field, inspect the particular referenced definition and record the edition and locator. [Published RFC](https://www.rfc-editor.org/rfc/rfc8348.html)

The list is keyed by component name within this server. The original also specifies what happens when hardware is detected. Where configuration is supported, an entry with matching class, parent and relative position can supply the component’s configured name. An unmatched detection uses values detected by the implementation. A configured slot, detected component and serial-numbered physical item can therefore require different labels in the Details view. This is an initial finding to test against the existing rows. [Section 7.1](https://www.rfc-editor.org/rfc/rfc8348.html#section-7.1)

## One bounded comparison and delivery

1. **Read from the donor outward.** Use the published inventory to cover identification, class and containment, configuration versus detection, replaceability, revision and manufacturer context, state, alarms, readings, freshness and change notifications. Group definitions with the same purpose and record the members, exceptions, operative passages, feature conditions and data access. Reconcile every item with a finding, documented overlap, scope reason or explicit hold. Distinguish the standard, the legacy appendix, vendor extensions and evidence of installed hardware.
2. **Compare in both directions.** Give each existing information row one explicit RFC decision with source, meaning, level of correspondence and classification. Test repeated explanations against individual row subjects. For each genuine new distinction, identify its nearest existing row and the information the client would lose by merging it. On each proposed addition, check all previously researched donor columns against relevant existing evidence and original sources as needed. Record qualified matches, scoped negatives and any genuine source holds in the corresponding comparison records. Keep the cross-donor coverage up to date when a new row is created.
3. **Deliver and stop.** Integrate the justified changes in the canonical JSON, both pairs of mirrors and the same editable Excel workbook. Preserve stable IDs, prior cells outside documented comparisons, sheet identities, colors, row-only freeze and version history. Verify the saved values and classification fills, compare a GitHub download with the local workbook, check published verification and report the concrete client implications. Stop for the owner’s assessment decision; no new proposal count is assumed.
