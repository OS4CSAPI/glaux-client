## 2. Original C239 source-native navigation and provisional semantic observations

This is a **targeted original-text intake, not a claim that every provision was audited**. The original C239 PDF cover/metadata confirms the publisher/edition/erratum (PDF pp. 1–2). Its table of contents (PDF pp. 3–7) separates physical Sensor/Host (§4), taxonomy and functional decomposition (§5), system management (§6), task and sensor functions (§§7–12), hardware (ch. 13), run-time environments (ch. 14), interfaces (ch. 15), source-native glossary (App. A), and **normative attached data model and OpenAPI artifacts (App. B)**.

| Source-native concept(s) and original inspected locator | Why it potentially matters for the DIM | Negative equivalence/remaining review question |
| --- | --- | --- |
| **SOSA sensor** — C239 §4.1.1.1, printed p. 21 / PDF p. 47 | Candidate correspondence to whole sensing System/arrangement (`S06-R005`) | Scoped SOSA reference architecture, not by itself the unique universal DIM root or proof of a physical deployed reference |
| **SOSA hardware element** — C239 §4.1.1.2, printed p. 21 / PDF p. 47 | Physical constituent (`S06-R007`) and optional aperture/chassis/PIC composition | Not equivalent to every hardware/software “component”, logical SOSA Module, current installed probe or strict hardwired sensor array |
| **SOSA host platform** — C239 §4.1.1.3, printed p. 21 / PDF pp. 47–48 | Hosting/mounting platform (`S06-R009`), power and navigation context | Not a source-authenticated surveyed sensor point, station operator or mandatory vehicle only; original App. A “Platform” is explicitly context-dependent (printed p. 361 / PDF p. 387) |
| **SOSA Module vs SOSA Infrastructure** — C239 §5.1 / Fig. 5.1-1, printed pp. 29–30 / PDF pp. 55–56 | Logical function, physical hardware, run-time and interaction-carrier separation | A functional module need not equal a physical part, one network-visible participant, a self-contained sensor or a procured physical unit |
| **Procurable SOSA unit** — C239 §5.3, printed p. 31 / PDF pp. 57–58 | Product kind/implementation grouping versus source-declared architectural roles | Native taxonomy does **not** dictate procurement/implementation multiplicities or a one-module-per-card mapping |
| **System Manager vs Task Manager** — C239 §5.4, printed p. 32 / PDF p. 58 | Equipment manageability, monitoring, fault/health and mission-task boundaries | Device housekeeping is not task success, an executed user command or measured physical effect; original 1.1 text says Task Manager module not ready for publication |
| **SOSA conceptual/logical/physical data levels** — C239 §5.7, printed pp. 35–36 / PDF pp. 61–62, with §B.1 printed p. 364 / PDF p. 390 | DIV-1/2/3 and mission versus management information are strong potential donor evidence for whole-system modeling | The referenced normative DSDM and IDL are **separate actual files**, not proven inspected by reading the descriptive body; no blanket correspondence to OGC SensorML/SWE/CSAPI |
| **Managed versus unmanaged component** — C239 §6, printed p. 38 / PDF p. 64 | Management representation may be direct or via a second SOSA component | A managed software/hardware role does not prove an actual live installed device or physical control |
| **Mode / State / Status** — C239 Appendix A glossary, printed pp. 360–363 / PDF pp. 386–389 | Important distinctions for existing `S06-R016`/operational-state candidates | Native mode, life-cycle state and health status are not the same datum; no direct ISA Config/Status or CSAPI binding assumed |
| **Power module** — C239 SvcV-1 summary, printed p. 27 / PDF p. 53; later ch. 12 and 13 not yet audited | Potential source role for conditioning, distribution, storage and control of power | Functional power module ≠ measured battery voltage, mounted power unit or single required power class |

The **physical-context figure** (PDF p. 47) was visually examined. It distinguishes SOSA elements inside a sensor boundary and the host platform; the architecture notes that depicted elements and relationships are optional. This visual context reinforces the semantic separation above but does not independently prove native DSDM classes or implementation conformance.

**Source review standing for these observations:** `ORIGINAL_C239_SELECTED_CLAUSES_INSPECTED_FOR_SCOPE`, **not** `FULL_SOURCE_CLAUSE_AUDIT_COMPLETE`, `DIM_MAPPING_APPROVED`, `DSDM_NATIVE_MODEL_INSPECTED`, or `SOSA_CONFORMANT`.
