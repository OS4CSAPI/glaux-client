# Step11 — SWE Common 3.0 original source/JSON schema review

**6 November 2026 · bounded Step11 technical result · 4 proposed donor-to-DIM correspondences, 13 held native-source leads.** All terms below derive from the approved [OGC 24-014, SWE Common Data Model Encoding Standard, version 3.0.0](https://docs.ogc.org/is/24-014/24-014.html) (16 July 2025) and its [official JSON schemas](https://schemas.opengis.net/sweCommon/3.0/json/). These source checks do **not** establish a compliant implementation or an adopted DIM.

## 1. What we learned, in ordinary terms

**SWE Common tells us how to describe and encode *data*, not what the whole equipment assembly is.** It provides a named-field `DataRecord`; semantically referenced data components; numerical `Quantity` with units; `Time` and `TimeRange`; categorical values; quality and missing-data controls; and typed arrays/streams. It does not automatically name a manufactured sensor, prove a field-installed system, create a performed Observation, or capture a ControlStream Command. This distinction is exactly why the standards columns belong beside each other.

Four existing proposed DIM rows have useful but qualified SWE Common correspondences: the output field itself, the property a value represents, the vocabulary of allowable mode values and a categorical value that *could* encode a reported mode. We **did not** change any DIM row, add a new mandatory module, or claim the latter two are evidence of actual operating state. Everything else is recorded as a source-backed lead to decide during model reconciliation.

## 4. How this helps the four equipment examples

**Dragino S31-LB:** `TempC_SHT31` and `Hum_SHT31` are native decoder/output names. A SWE `DataRecord` can describe two named fields and their distinct `Quantity.definition` and units. That does **not** create two hardware probes, verify actual measurements, or prove the manufacturer publishes SWE JSON.

**AirGradient Open Air Max:** `pm01`, `pm25` and `pm10` are separate particulate-property *data fields*. They are not the same things as the two physical PMS5003 modules and PM1/PM2 hardware sockets. A SWE Common field descriptor preserves that separation; we cannot infer actual installed modules, live status, corrected-gas calibration or valid analytical data from a published example.

**Campbell CR1000X + ClimaVue 50:** the published `aR7!` reply has 14 defined positions; the separate logger `Status` publication has 31 example fields. SWE Common fields could describe their source-native names/types/units **separately**, not imply one physically verified station, 14 sensors, or that logger `PanelTemp` measures outdoor air temperature.

**Bennett's Point:** the NOAA original `ATemp` fields carry two historical 15-minute means. `TimeRange` could encode two known bounds, `Quantity` could encode a known numeric temperature and a `Category`/`Text` descriptor could preserve QA. But original `F_ATemp="<0> "` (including trailing space) and separate blank `F_Record` must not be silently normalized. The original source doesn't establish `resultTime`; four older experimental digital representations still refer to two original means, **not four observations**.

## 5. Source/version/interpretation discipline

- **Units:** Original §8.2.8, §9.1.9 and Requirement 59 require quantities to carry a unit/scale. A unit code should conform to Unified Code for Units of Measure (UCUM) or a resolvable URI when appropriate; when both are present, they must agree. Unit name, quantity semantics and native value must be recorded separately. A percentage or humidity fraction is not automatically interchangeable without an explicit conversion.
- **Data field vs hardware:** `DataRecord.fields` (original §8.3.1) groups heterogeneously typed named *data components*. A `DataRecord` does not identify a physical port, transducer channel, IP participant or system component.
- **Time:** `Time` and `TimeRange` (original §§8.2.9/8.2.14, Requirement 84) support temporal values/ranges, not OGC OMS `phenomenonTime`/`resultTime` assertions without source evidence. A nominal interval we derived from a record's cadence is not an original timestamp.
- **Quality/nils:** §8.2.15 Quality and §8.2.16 NilValues permit representations of quality statements and missing-value reasons. Neither authorizes invented QA/health readings or treating zero as absence.
- **Categories:** §8.2.6 and Requirement 24/25 permit controlled categorical tokens, including operational mode labels. **That is a representation mechanism, not proof an installed individual supports or currently uses a mode.**
- **DataStream:** SWE Common `DataStream` is a low-level payload descriptor/encoding container (§8.5.3); it is not automatically the **OGC API – Connected Systems Part 2 DataStream resource** or a network transport/session.
- **Original JSON:** 24-014 v3.0 is not the XML encoding of earlier SWE Common 2.0. The official JSON schema URLs identify the source-native representation; no live device payload, JSON Schema processor or OGC conformance suite was run in this step.

## 6. A real publication ambiguity worth holding

In the exact **OGC 24-014 §10.2.3, Requirement 85(A)**, the text describing `recordsAsArrays` reverses its polarity: it says `true` results in JSON objects and `false` in arrays, whereas the nearby §8.7.1 description and §10.2.3 introductory text state that `false` is the default for JSON objects and `true` selects arrays. This appears to be a **standard-document inconsistency**, not a source-derived permission to invent an implementation rule. No field in the master was populated based on one side of the contradiction. We should only settle it using an authoritative clarification, official erratum or conformance outcome when an encoder is implemented.
