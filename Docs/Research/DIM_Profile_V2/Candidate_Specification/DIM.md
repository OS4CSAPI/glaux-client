## Step 16 — Described subject, individual, kind, evidence and digital representation

**Standing: INITIAL PHASE D CANDIDATE DEFINITIONS · 2 November 2026 · NOT ADOPTED / NO TRANSFORMATION TEST.** This is the first bounded identity/description portion of the connected DIM envisioned by [Gate C](../Whole_System_Recovery/README.md#19-step-15--phase-c-comparison-bounded-working-subject-and-gate-c). Its proposed distinctions apply to a **source-grounded sensing System/arrangement focus** and do not determine a final domain name, universal superclass, implementation syntax, mandatory classes or one-to-one mappings into OGC API – Connected Systems (CSAPI). **The source must establish whether the described subject is a reusable design/reference or a particular real-world individual.**

### Proposed meaning of the described subject

A **described subject** is *the thing or reference arrangement about which a specific assertion is made*. The subject can be a **reusable kind**, a **reference combination of equipment**, a **specific identified equipment item**, or an **actual continuing station/System**. Calling a reference combination “the S31-LB arrangement” or “the CR1000X/ClimaVue pairing” does **not** assert that a particular deployed combination exists. Selecting the subject for one information view is an **interpretation decision**, not automatically creating a new real-world object or a DIM root class.

The source's **identity assertion and its authority/temporal scope** determine whether a real individual has been established. A System can have a stable, source-identified focal identity despite hardware replacement (as with the **Bennett's Point station**), but that station identity is different from the identity of each serialized probe used there. Other sources may establish an individual sensor without any station, or a product design without any particular sensor. **The DIM cannot require a deployed station for every subject, nor infer physical parts by counting output fields.** Physical composition, hosting and role intervals will be developed in later steps, not defined here.

### Candidate term meanings — separate referents, not a six-class ontology

| Candidate meaning | Bounded definition for drafting | Source-backed positive / prohibited shortcut |
| --- | --- | --- |
| **Individual sensing System or equipment referent** | A **particular real-world identified subject**, equipment-realized whole, equipment item or continuing monitoring arrangement, whose identity is asserted by an appropriate original source at a stated scope. The whole and its equipment participants may be *different individuals*. | Bennett's operator identifies station **acebpmet**, logger serial **13916** and two distinct EE181 probes. **Do not** treat the station code as the probe serial, or demand that a persistent station be a single manufactured box. |
| **Product kind or model description** | Reusable manufacturer/design information describing a **type, model or known equipment configuration**; it may specify supported capabilities and technical parameters without naming or testing a particular individual. | Dragino **S31-LB**, AirGradient reference **O-M-1PPSTON-CE**, Campbell **CR1000X** and **first-generation ClimaVue 50** are product/design descriptions. A model string **is not** an installed unit; AirGradient **-CE-S** is not automatically the same edition/configuration. |
| **Reference arrangement** | A *design-level assertion* that specified product kinds may be **connected/combined** in a documented way. This does not itself provide a real-world unit/station identifier or current installation. | Campbell documents one ClimaVue plus a CR1000X and SDI-12 wiring **as a reference pairing**. The unrelated 2019 program and 2026 logger Status example cannot be joined into one installed station. **A reference arrangement need not be treated as another manufactured product kind.** |
| **Original source record or assertion** | An attributable manufacturer document, equipment-use entry, archive row, message, program example or other **evidence item that makes a claim**, identified in its native scope, version, publication/measurement context and original content where available. It can describe *kind, individual, process, event or representation*. | The NOAA **acebpmet2024.csv** air-temperature rows identify station/date/parameter and QA, **not probe serial**. The reserve's *separate equipment history* names EE181 serials and service dates. Joining them is **project-derived attribution**, not an additional original CSV field. |
| **Digital description or resource** | A digital information artifact, API resource, metadata/knowledge representation, Shell/Thing Description or server description about an explicitly referenced subject or type. **Its own identifier identifies the description/resource** unless a source asserts a different subject identity. | AAS **AssetAdministrationShell** has its own identity distinct from **AssetInformation** for the represented asset; CSAPI has **resource-local IDs/URLs** and source-qualified System UIDs; WoT Thing Descriptions can describe physical **or virtual** Things. **No generic URI-to-serial identity inference.** |
| **Mediated network participant, reporter or proxy** | An interface/service/actor that may **expose, publish, relay, cache or represent** source information. Its sender/resource identity and the original subject/performance identity may be different. This is a *role distinction*, not a claim every API is a twin or that a new proxy class is compulsory. | SAPIENT **node_id** is the message sender UUID; ISA's composition interface can expose an opaque member's capability; WoT **Intermediaries/Digital Twins** can change digital ID or provide cached information. **Do not** equate sender/proxy/response identity with original hardware. |

**Interpretation and classification note:** These are candidate **meanings that may eventually be represented using roles, relationships, attributes or existing standards constructs**. A text row is **not automatically a new DIM entity**. For example, *reference arrangement* may simply be an evidence-scoped description of several product kinds, and *digital proxy* may be one supported interface role rather than a universally installed component. No one-to-one ontology correspondence with AAS, OMS, SSN, WoT or CSAPI is declared.

### Candidate relationship meanings — read as propositions, not implementation keys

| Proposition to preserve | What evidence would support it | Incorrect identity claim that is rejected |
| --- | --- | --- |
| **Source record asserts about → described subject** | A publisher's native record, section, observation row, identifier or documented subject with stated **source/edition/time** and whether the claim is **design, example, actual history or derived**. | A source's document ID or record URL **is** the physical sensing System. |
| **Product kind is applicable to → individual or reference role** | An original identified model designation for that item or a manufacturer-defined design role. If unresolved, record **kind unknown** or alternative descriptions, not a guessed type. | Every two objects with identical model names or externally reported types **are the same individual**. |
| **Source asserts identifier → specific referent** | Original value **plus identifier scheme, issuer/authority, referent, scope and source record**; preserve exact native spelling. Time/version qualifiers where the evidence supplies them. | Same string, local address, CSAPI ID or metadata field automatically identifies the same physical unit across services/periods. |
| **Digital description represents → subject of description** | Explicit, source-qualified statement about **which kind, physical individual, station, interface role or group** the representation is intended to describe. | AAS Shell, SAPIENT Node UUID, WoT TD ID and CSAPI System resource **all have to be** the manufacturer's serial or each other's URI. |
| **Digital participant reports/mediates → source assertion or capability** | Evidence of the **reporter, original producer where known, any forwarding/cache/derived standing, original message/version and temporal meaning**. | A value received from a proxy was directly and freshly sensed by that proxy, or a relay proves the equipment inventory. |
| **Evidence-derived identification or attribution → asserted referent** | Traceable inference with **input source records, explicit join conditions and uncertainty**; must stay different from direct source identity. | Project's Bennett **date-based probe attribution** is a physical serial **present in** the original NOAA temperature row. |

**Minimum identity-claim explanation, not a mandated field schema:** When asserting that a value **identifies** an individual, be able to say **what it identifies**, **who issued the identifier**, **under which scheme or source context**, **where the original value and statement came from**, and **what period or edition makes the assertion meaningful**. Those details may be unknown; the DIM must preserve rather than conceal that uncertainty. A **manufacturer serial**, **station code**, **SDI-12 address**, **IEEE channel/UUID**, **SAPIENT Node ID**, **CSAPI local resource ID**, **source row number**, and **WoT proxy/TD ID** are not automatically aliases. No universal one-Identifier-per-System cardinality, manufacturer-serial requirement or guaranteed alias resolution is adopted.

## Step 17 — Physical constituent, external connection, functional realization and hosting

**Standing: PHASE D CANDIDATE RELATIONSHIP MEANINGS · 2 November 2026 · NOT ADOPTED / NO TRANSFORMATION TEST.** Continue the [Step 16 distinctions between an individual, product description, reference arrangement and digital representation](#step-16--described-subject-individual-kind-evidence-and-digital-representation), under the [Gate C source-bounded focal-System approach](../Whole_System_Recovery/README.md#19-step-15--phase-c-comparison-bounded-working-subject-and-gate-c). This step answers **how participating equipment relates to the focal System**, not **how a sensor's individual channels, outputs or observed properties are encoded**; those are Step 18 and later work.

### The essential distinction

A **whole sensing System** is not necessarily one box, and a device **connected** to that whole is not automatically **physically contained** by it. Likewise, **performing a function** and **hosting or managing another participant** do not, on their own, establish physical ownership or assembly. The same manufacturer product can contain several boards, have an external probe supplied with it, communicate with other independent equipment and rely on services outside it. Conversely, a separately identified station may persist while its actual sensing equipment changes.

**Working principle:** identify a source-attested focal System or *reference* arrangement, then describe each physical, functional, communication, hosting or supporting relation **only at the subject and evidence scope established by the original source**. Source-authored product assembly information can be valid **at design level** without creating any real installed serial-numbered member. A documented physical unit in an equipment-use log has stronger individual standing than a product's named option, but that log still does not prove arbitrary internal parts or exact installation times.

### Candidate relationship meanings and their separate evidence tests

| Candidate relationship question | Proposed meaning and qualifying evidence | What must NOT follow |
| --- | --- | --- |
| **Is this a constituent of a described physical assembly?** | An item is specified by the manufacturer or operator as **part of the physical build** of the identified whole, at either **reference-product** or **identified actual-unit** scope. Evidence may describe a main board, fitted sensor module, structural item or built-in physical subsystem. A physically distributed assembly may be a whole when its boundary is explicitly established. | **Not equivalent to:** spatially *inside an enclosure*; merely cabled to another device; exposed through its API; one reported quantity; or a guaranteed installed serial-numbered part. A physical constituent need not have its own independent management or CSAPI resource. |
| **Is it a supplied/associated external element of a design?** | A source can describe equipment provided as part of a product **while physically external to its principal housing**, such as a tethered probe. Distinguish being **included in the manufacturer reference arrangement** from where it is mounted or whether it has independent unit identity. | **Not equivalent to:** built into the radio node or necessarily a separately managed, replaceable or installed individual. The source may not settle the exact physical part/ownership boundary of the cable and probe. |
| **Are two independently described equipment items connected?** | An original wiring/interface source establishes **electrical, data, bus or other connection** between distinct equipment subjects, optionally including physical interface endpoints and a source-native bus address. A design-level wiring possibility and a verified actual wire are different assertions. | **Not equivalent to:** physical containment, common manufacturer product identity, one combined fielded station, one observer, or proof a command traversed the interface. |
| **Does an item physically host, mount, support, or group another subject?** | A source may identify a **platform, rack, mast, enclosure, monitoring station or organizational Host** and link equipment to it. State **which meaning of host** is supported—physical support/mounting, operational station grouping, processing host or digital information host—and whether the relationship is historical, current or merely proposed. | **Not equivalent to:** a permanent part-of relation, spatial position known for each probe, physical ownership, or exact time-scoped Deployment. A service exposing a device in its AddressSpace is not a hardware mounting structure. |
| **Which hardware or software realizes a sensing, processing or reporting function?** | A source links equipment or software to its **performed/designed responsibility**: sensing, computing, acquiring, recording, relaying, controlling or managing. **Functional realization can be distributed**, and one physical item can participate in more than one function. | **Not equivalent to:** one physical unit per function, one SensorML process per chip, one channel per output field, a verified executed program, or proof the function's reporting participant is the physical observer. |
| **Who supplies power, communications, management or other support?** | A relevant support relationship may describe a power path, bus, controller, network device or manager where the source establishes the participant and scope. The physical support item may be built in, plugged in, external or merely an available option. | **Not equivalent to:** automatic internal construction, active mode, current health, power state, successful task execution or a universal power/management-first architecture. |
| **What is merely exposed or represented digitally?** | The [Step 16 representation/mediator relationship](#step-16--described-subject-individual-kind-evidence-and-digital-representation) remains a **separate axis**. A manager or proxy may expose a capability or information *about* equipment without being that physical unit. | **Not equivalent to:** discovering all physical constituents or a physical part-of link from API nesting, a digital Shell, intermediary ID, logical hierarchy or reporting topic. |

These are **candidate relationship questions/propositions**, not seven compulsory UML associations, newly standardized property names, CSAPI resources or always-present UI sections. **Two claims may simultaneously be true:** an AirGradient sensor module can be *physically part of a product assembly* **and** *communicate over I²C*; Dragino's cabled probe can be *supplied in the reference product* **and** *outside the radio housing*. The model must preserve both claims when attested and must not infer either from the other.

**Explicit type versus individual level:** “the O-M-1PPSTON-CE reference has two PMS5003 devices” is a **manufacturer design claim**. It is **not** evidence that two particular serial-numbered PMS5003 units were observed in a physical monitor. “EE181 serial 222016000109CE served at Bennett's Point in a recorded period” is **operator source history** about a particular unit and station, but the exact changeover minute and an individual probe's independent geometry remain **UNKNOWN**. No mandatory single-parent tree, transitivity, fixed cardinality, or one-connection-equals-one-part rule is established.

### Native donor grounds and important open distinctions

- **OPC UA Devices Part 100 v1.05.0** explicitly distinguishes the **Device Model** for hardware/software parts, a **Device Communication Model**, and a **Device Integration Host Model**. Its [§5.5 ConnectsTo](https://reference.opcfoundation.org/specs/OPC-10000-100/5.5) is **symmetric and NonHierarchical** for network topology, not an intrinsic physical part-of relation. [§9.4 Modular Devices](https://reference.opcfoundation.org/specs/OPC-10000-100/9.4) supports a source-native modular-device description. These are **separate OPC UA models**; no OPC UA Conformance claim about our four vendors follows.
- **AAS Part 1 v3.2** distinguishes **Entity** in a composite asset description, self-/co-managed entity representation and explicit **RelationshipElement** semantics. It contributes management and composition granularity, but **self-managed does not prove one physically enclosed independently verified sensing unit**, and source AAS cardinalities are not universal DIM rules. [Original SubmodelElements/Entity](https://industrialdigitaltwin.io/aas-specifications/IDTA-01001/v3.2/spec-metamodel/submodel-elements.html).
- **SensorML 3.0, OGC 23-000 §§7.1–7.2 and 8.4–8.6** models physical and computational **processes**, including aggregate components and **connections**, and its **PhysicalSystem** is a process-oriented *described physical aggregate*. It is not an ontology assertion that every connection is mechanical containment or every process a piece of hardware. [Original approved SensorML HTML](https://docs.ogc.org/is/23-000/23-000.html).
- **The Open Group SOSA** describes a multi-element whole **Sensor** and a distinct **Host Platform**, with functional Modules versus infrastructure and manufactured/implemented components. This is a powerful source distinction, **not** a universal environmental DIM root or an OMS Host equivalent. [Original-edition review, workbook §16](../Whole_System_Recovery/README.md#16-step-12--isa-60-and-the-open-group-sosa-physical-functional-visible-and-managed-relationships).
- **ISA 6.0, OMS 3.0 and W3C/OGC SSN 2017** separately illustrate **visible/opaque component representation**, **Observer versus Host/Deployment**, and **System/Platform/hosted-on/subsystem**. Their different “component,” “host,” and “system” terms **are not cross-standard synonyms**. [Native source inspection §§16 and 18](../Whole_System_Recovery/README.md#18-step-14--sapient-v2-oms-30-w3cogc-sosa-ssn-and-web-of-things-observation-action-time-and-representation). ## Step 18 — Interfaces, addressable channels, reported outputs, fields, properties and reporters

**Standing: PHASE D CANDIDATE RELATIONSHIP MEANINGS · 2 November 2026 · NOT ADOPTED / NO TRANSFORMATION TEST.** This is the next bounded part of the [working whole-System approach selected at Gate C](../Whole_System_Recovery/README.md#19-step-15--phase-c-comparison-bounded-working-subject-and-gate-c). Preserve the [Step 16 subject/identity distinctions](#step-16--described-subject-individual-kind-evidence-and-digital-representation) and [Step 17 physical versus connected/functional/hosting relationships](#step-17--physical-constituent-external-connection-functional-realization-and-hosting). Step 18 distinguishes **what hardware realizes sensing, how it is accessed, what its interfaces expose, what a report contains, what each field means and who reports it**. It does **not** decide actual Observer/Observation/procedure/time/quality meaning (Step 19), an OGC API – Connected Systems (CSAPI) DataStream producer mapping (Phase E), or how Glaux must render these facts.

### Why these distinctions are indispensable

One documented **Dragino SHT31** is an external physical temperature/humidity sensing probe, yet the S31-LB radio node can report **both quantities**, battery voltage, time and status bits through different **LoRaWAN FPort message forms**. Counting message fields as physical probes would misdescribe the equipment; counting the FPorts as addressed transducer channels would also invent a different interface model. An **AirGradient** monitor has **two physical PMS5003 instruments at PM1/PM2 connector positions** alongside several other sensing modules, but its published PM1.0, PM2.5 and PM10 fields describe **quantities**, not the PM1/PM2 connector identities. **Campbell's ClimaVue 50** returns **14 defined value positions through one SDI-12 aR7! response**, while a separate CR1000X logger can read and transform sensor values and exposes its **own logger-only Status**. Neither the 14 positions nor a later logger Status record proves 14 physical units, 14 separately addressed channels or one actual operating station.

**The critical scope test:** the same original source may establish a physical component, a bus or service interface, a logical address, a message schema, a field and a quantity, **but those remain different referents/roles unless the source explicitly relates them**. Multiple physical sources can contribute to a single reported structure; a single physical sensing element can contribute several described values; an output can contain measurements and administrative values in the same record. A reported number alone does not identify the individual sensor, observation procedure or original observer.

## Step 19 — Observing capability, performed Observation, subject, result, time and quality

**Standing: PHASE D CANDIDATE OBSERVATION MEANINGS · 2 November 2026 · NOT ADOPTED / NO EXECUTABLE TRANSFORMATION.** Continue [Step 16 identity/source/representation](#step-16--described-subject-individual-kind-evidence-and-digital-representation), [Step 17 physical and functional relationships](#step-17--physical-constituent-external-connection-functional-realization-and-hosting), and [Step 18 interfaces/outputs/reporting provenance](#step-18--interfaces-addressable-channels-reported-outputs-fields-properties-and-reporters). This section separates **documented observing capability and reusable method** from **an observation activity known to have occurred**, its physical or computational participant(s), the characteristic and environmental subject involved, the result, source-relative time and quality. This is an **implementation-independent candidate reading**, not a mandatory class list, a CSAPI observation encoding, a DataStream-producing-System decision, or a complete historical observation dataset.

### The source must first prove that an observation happened

**A technical datasheet says what an instrument could do. A result record with documented observational provenance can establish evidence of something that was done.** This difference is decisive across our corpus. Dragino's published decoder examples, AirGradient's firmware/cloud examples, and Campbell's response-position and logger-status examples demonstrate supported/reportable behaviors **without identifying a real physical unit actually observing conditions**. The original **Bennett's Point / acebpmet 2024 NOAA/CDMO temperature rows**, in contrast, are actual station-published historical results. They support two selected real **15-minute mean air-temperature reports** without proving every underlying 5-second sample, executed logger source-code version, all sensor-level observation acts, exact result-availability instant or an individual Observer identifier present in each archive row.

**An Observation is not a sensor, a product type, a result number by itself, a logger-program example, or an API resource.** In **OGC Observations, Measurements and Samples (OMS) 3.0, OGC 20-082r4 §8.2.2**, the conceptual Observation is an *act* by an identifiable Observer to determine an ObservableProperty of a featureOfInterest by using an ObservingProcedure, yielding a result. OMS §8.5 distinguishes reusable **ObservingProcedure** (the description of a method, not an individual instrument) from **Observer** (§8.6: a particular identifiable sensor/instrument, algorithm implementation or person). Its meaning is broader than “one physical chip”: if an averaging algorithm creates a further result, the **physical sensing performer, processing participant and source-publishing service may have distinct roles**. The exact observer of a particular compound/processed result must be supported by its source, **not selected automatically from whichever System is easiest to query**.

### Bounded candidate meanings and original-evidence tests

| Meaning or association | Candidate interpretation and what must be supported | Incorrect inference explicitly rejected |
| --- | --- | --- |

## Step 20 — Configuration, operating state and condition

**Standing: PHASE D CANDIDATE SEMANTIC DISTINCTIONS · 2 November 2026 · NOT ADOPTED / NOT RUNTIME-TESTED.** Continue the [Step 16 identity/source distinctions](#step-16--described-subject-individual-kind-evidence-and-digital-representation), [Step 17 physical/functional relationships](#step-17--physical-constituent-external-connection-functional-realization-and-hosting), [Step 18 interfaces/output/reporting](#step-18--interfaces-addressable-channels-reported-outputs-fields-properties-and-reporters), and [Step 19 Observation/time/QA meanings](#step-19--observing-capability-performed-observation-subject-result-time-and-quality). This Step 20 concerns **what behavior or setting is supported; what is described as default, desired, selected, applied or reported; which mode or operational state is asserted; and what equipment diagnostics or health/condition statements establish**. It does **not** model a request/Task's acknowledgement or completed effect (Step 21), time-bounded installation/replacement (Step 22), a power-centric taxonomy, mandatory DIM classes, or a CSAPI Profile binding.

### The problem: defaults, desired settings, effective state and condition are not interchangeable

A manufacturer can say a device **supports an interval or mode** without supplying an individual unit, and can state a **default** without showing what a user selected or what a fielded device actually used. A controller's *desired/offline* settings can differ from the *online* equipment values. A status report can describe **last-reported operating state at a time** without proving it remains current. A diagnostic such as voltage or scan-count can describe one component's operating behavior **without proving a whole station is healthy**, just as a recorded sensor-health warning does not specify its configuration. Modes can be named settings, operating regimes triggered by measured conditions, or publisher-specific state labels; the candidate DIM must preserve the **original source's meaning and participant** rather than forcing all modes into one Config class.

**Source-evidence principle:** For any setting, status or condition assertion identify the **subject (device, component, software or station), exact property and unit/value, original issuer and source/edition, status of the claim (design, example, actual historic or directly reported), and effective or report time when established**. A reporting intermediary or publisher does not automatically provide direct physical state; an old readback is not current merely because the client retrieved it now. **UNKNOWN** is not the same as false, zero, unset or a fault.

### Candidate meanings — conceptual roles, not eight universal DIM classes

| --- | --- | --- |

## Step 21 — Command availability, issued request, acknowledgement, outcome and evidence of effect

**Standing: PHASE D CANDIDATE CONTROL/ACTION SEMANTICS · 2 November 2026 · NOT ADOPTED / NO LIVE COMMAND OR STATE-CHANGE TEST.** Continue the [Step 16 individual/source/representation identity distinctions](#step-16--described-subject-individual-kind-evidence-and-digital-representation), [Step 17 physical/functional relationships](#step-17--physical-constituent-external-connection-functional-realization-and-hosting), [Step 18 interface/output/reporter meanings](#step-18--interfaces-addressable-channels-reported-outputs-fields-properties-and-reporters), [Step 19 performed Observation and time/quality](#step-19--observing-capability-performed-observation-subject-result-time-and-quality), and [Step 20 desired versus effective setting, status and condition](#step-20--configuration-operating-state-and-condition). ### Why this separation is needed

**A command being available does not mean anybody sent it.** A request being sent does not prove it arrived, an acknowledgement may only confirm receipt or acceptance, and a source reporting task completion does not independently prove that a physical or environmental outcome occurred. A later changed status can be evidence of a device's reported state **without by itself proving which request caused the change**. Source examples or simulator templates are **documentation/examples, not captured operating exchanges**. A command may seek a configuration change, measurement, camera pointing, movement, calibration, restart or data retrieval; its purpose and its success conditions must stay **source-specific**.

This is not an invented sequence of compulsory states. An original protocol may report multiple outcomes, may omit a particular stage, may use a status readback without a task ID, or may involve an intermediary. A source can declare **COMPLETED** as its task's state while a physically measurable consequence still remains **unverified**. The candidate DIM must keep each **assertion, its issuer, target, correlation keys, original message/time scope, meaning and evidence grade** distinct.

### Bounded candidate meanings — source assertions, not ten new classes

| Conceptual distinction | Meaning or evidence condition | Incorrect shortcut to reject |

| **Supported command / operation definition** | Source-specified capability, target type, operation syntax, parameters, conditions, preconditions and possible outcomes at the product, software interface or protocol edition scope. | Manufacturer command table or SAPIENT Registration means an actual individual unit received a request or performed an action. |
| **Issued request / Task** | Evidence of a particular command invocation with **originator, intended target/recipient, request identifier if present, operation, arguments, source and request-issue time**. A printed example is a **SOURCE_EXAMPLE** of an issued-request *form*, not evidence a real request was sent. | An available control, example packet or selected setting is an actual command execution. A request's own ID is automatically the physical target's ID. |

### Native donor pedigree and the Deployment ceiling

**OGC Observations, Measurements and Samples (OMS) 3.0, OGC 20-082r4** [§§8.6–8.8 and 9.8](https://docs.ogc.org/as/20-082r4/20-082r4.html): **Observer** is an individual identifiable observing entity; **Host** is a grouping of Observers (a monitoring facility is one example); **Deployment** is information about the **assignment of an Observer to a Host**. No source PDF/CSV, frozen corpus, original example, CSAPI Profile, Glaux app, 52°North/Oracle server or Cloudflare deployment was changed. ## Step 23 — Cross-cutting whole-System services, assertions and evidence limitations

**Standing: PHASE D CANDIDATE COVERAGE QUALIFIERS · 2 November 2026 · STEP 23 COMPLETE, GATE D OPEN · NOT ADOPTED / NOT A NEW SEVEN-MODULE ONTOLOGY.** Based on the [Step 23 four-case/source review in workbook §27](../Whole_System_Recovery/README.md#27-step-23--cross-cutting-whole-system-coverage-and-evidence-gaps), this section **qualifies** the relationships developed in Steps 16–22; it does not prescribe a universal power interface, security policy, software-update machinery, maintenance log, output/QA field, or mandatory package. **Step 24** must determine how these qualifications connect within one integrated draft and challenge it against the actual case evidence. No Profile clause, CSAPI mapping, client behavior or runtime result is adopted here.

### The modeling question: whose power, connection, software, security, provenance, quality or maintenance?

A whole sensing System has more than sensors and observations, but **a documented possible capability is not an actual running service**. In the four evidence cases, the reported diagnostic may concern a **radio node**, **battery**, **particulate-sensing board**, **weather sensor**, **logger**, **station**, **publisher**, **message**, **software version** or **one historical measurement**. It is a modeling error to promote one such fact to an unsupported status of the whole. Cross-cutting means **a documented relationship or assertion can qualify more than one of our existing subjects**, not that every subject must contain every heading.

The draft should be able to ask the following source-qualified questions; the expressions below are **analyst candidate interpretations**, **not mandatory named DIM associations, universal classes, cardinalities or serialization keys**:

| Cross-cutting question | Minimum preserved distinctions / bounded candidate relationship | Inappropriate inference |
| --- | --- | --- |

Distinguish source-design chemistry/capacity/supply limits from a reported voltage, a component-specific power-on state, actual charge, estimated remaining life and the identity/time of the reading. ## Components and channels

**One probe can measure two things.** The [Dragino S31-LB manual, §§1.1–1.2 and 1.8](https://wiki.dragino.com/docs/LoRaWAN-End-Node/temperature-humidity-sensors/s31-lb/) specifies one external SHT31 probe; the temperature and relative-humidity quantities do not turn it into two probes. Conversely, a single interface can report information from several components. A usable model must be able to draw both arrangements without changing the meaning of “part.”

### Proposed definitions and relationships

| Relationship, read left to right | Meaning in this draft | What establishes it |
|---|---|---|
| **Assembly has physical part → equipment item** | The item belongs to the physical construction of the described assembly. In a product description this is a design claim; in an installation it concerns particular equipment. | Evidence of physical construction or installation at the stated level. A shared housing is not required; a cable alone does not settle permanence or interchangeability. |
| **Implementing item realizes → function** | The hardware, software, or combination performs a defined role in the design. A function is not itself another item in the physical inventory. | Evidence linking the role to the implementing item. Retain a known function even when its implementation is not identified. |
| **Interface exposes → addressed channel** | A source distinguishes an access point for transducer data or control in a particular addressing context. Preserve the source's local address and the context needed to resolve it. | Source-defined addressing or service evidence. A message field, unit or network port alone does not establish a transducer channel. |
| **Reporting system exposes → output; output contains → field; field denotes → property** | An output is a declared result structure. A named field describes a value in that structure; a measurement field identifies the property represented and, when applicable, its unit. A scalar output need not be wrapped in a record. | Output/schema documentation. Link an output to a contributing component or channel only when the source supports the association. The reporter and the sensing element need not be the same. |

These are relationship names in the draft, **not JSON keys**. None of the four is derived simply from the existence or number of the others. Repeating a local channel address under another interface does not establish identity. Renaming a field does not change the physical inventory. A design-stage part reference does not identify a deployed unit.

### Why these choices

The Open Group's Sensor Open Systems Architecture distinguishes functional modules from the hardware and run-time infrastructure that supports them (Reference Architecture ed. 1.1, §5.1, Fig. 5.1-1); its distinct ed. 1.0 Domain-Specific Data Model also links `Product` and functional `Component_` through `ProductInstance` (§§1.1.3.15, .82–83). The Integrated Sensor Architecture explicitly allows an interface to expose the capabilities of an opaque member as its own (Software Design Document 6.0r5, §4.2.2 and Fig. 2). These originals support two different relationships—realization and exposure—neither of which is sufficient evidence of physical composition. [Original-document locators](../Donor_Challenge/04_Other_Structural_Challenges.md).

IEEE 1451 supplies a positive reason to keep the addressed channel: operations can target a channel in module context, and characteristics can belong to that channel. See the [NIST-hosted authors' service examples, Tables 1 and 3](https://tsapps.nist.gov/publication/get_pdf.cfm?pub_id=927142), the [channel TEDS example](https://www.nist.gov/el/intelligent-systems-division-73500/channel-teds), and the [2024-linked Playground source trail](../Donor_Challenge/03_IEEE1451_Challenge.md). These are public technical sources, not a claim to have checked every requirement in IEEE 1451.0-2024. A channel can correspond to actual hardware; this design requires a supported link rather than treating that correspondence as universal.

[SensorML 3.0 §§8.4–8.6](https://docs.ogc.org/is/23-000/23-000.html) separates process components from their outputs and data-flow connections. [Observations, measurements and samples (OMS) 3.0 §§8.3.2, 8.6.2–3](../Primary_Sources/OGC_20-082r4_OMS_3.0.0.md) distinguishes an observer from the property it can observe. The property is a characteristic of the feature being observed, not a part of the probe. Those ideas support preserving both the component and the meanings of its output fields; they do not imply one stream or one observer per field.

**Choice rejected for this draft:** a single tree in which every physical part, function, interface channel and output field becomes a child System. That tree would miscount the Dragino probe and hide the difference between what is built, what is addressable, and what is reported. The opposite shortcut—discarding all channels and retaining only measurements—would lose an IEEE channel's addressing context and channel-specific description. The [side-by-side table](../Concept_Donor_Comparison/Donor_Terms_Side_by_Side.md#components-and-channels) shows exactly where the donors align and where they do not.

## Temperature of what?

**Candidate decision.** Identifying a field's source component and unit is not sufficient to identify its meaning. Describe **which characteristic** the field represents and **what kind of thing has that characteristic** when the source establishes it. For an actual observation, the particular subject of the observation is a separate relationship from the instrument that made it. A design can establish the kind of subject without identifying an individual or supplying any result.

| Meaning in our model | OMS 3.0.0 | W3C/OGC SOSA (2017) | I-ADOPT 1.1.0 | Connected Systems 1.0 / SWE Common 3.0 |
|---|---|---|---|---|
| **What characteristic is this field about?** | `ObservableProperty`; observation → `observedProperty` | `sosa:observedProperty` | `Variable` → `hasProperty` (e.g., temperature) | Field `definition` identifies the specific property; `Property.baseProperty` can identify its more general characteristic. |
| **Of what?** | `featureOfInterest` is the subject of an observation | `sosa:hasFeatureOfInterest` identifies the subject of an observation | `Variable` → `hasObjectOfInterest` describes the entity role in the variable definition | `Property.objectType` identifies an entity **type**. It does not identify an observed **instance**. |
| **What made the observation?** | Observation → `observer` | `sosa:madeBySensor` | The instrument is not supplied by those two variable-definition relations | The producing `System` is associated with a `DataStream`; component/output attribution is preserved separately when known. |

These are our comparisons of roles, not cross-standard declarations of class equivalence. The [I-ADOPT Framework ontology v1.1.0](https://i-adopt.github.io/ontology/) gives a positive design contribution: keep the characteristic and its object explicit in a reusable variable meaning. [OMS §§8.2.6–7, 8.2.10, 8.3.2](../Primary_Sources/OGC_20-082r4_OMS_3.0.0.md) and the [2017 Semantic Sensor Network Ontology §§4.3, 4.6](https://www.w3.org/TR/2017/REC-vocab-ssn-20171019/) explain the observation-specific roles. Do not transfer I-ADOPT cardinalities or turn a product datasheet into an observation. [Connected Systems Part 1 §15.2.2, Table 19](https://docs.ogc.org/is/23-001/23-001.html) supplies a type-level representation; it does not replace those observation-level associations.

**What the second system changed:** the first example distinguished *one probe* from *two quantities*. Campbell also has two temperature fields from **the same weather instrument in the same unit**: the temperature of the air and that of the humidity sensor. Even grouping fields by their source component would not distinguish them. Conversely, air temperature from Dragino and air temperature from ClimaVue can share a property definition. Shared meaning permits discovery and comparison; it does not establish equal methods, a common site/time, interchangeable readings, or an actual reading in the first place. [See what each source actually supplies and how the Profile represents it.](CSAPI_Profile.md#campbell-temperature-of-what)

## Which setting applies?

**Candidate definition.** A *configurable parameter* identifies an aspect of equipment behavior for which a value can be selected. An *operating mode* is a named choice of behavior; it may select several parameter values together. A transmit interval is a parameter, not necessarily a mode. Either can be described without knowing what an individual unit is using.

| Relationship | What it means | What it does not establish |
|---|---|---|
| A design or unit **supports** a parameter, permitted values or modes | A source declares what can be selected for that subject. Retain units, constraints and applicability when given. | That a particular value was selected; that illustrative values enumerate the allowed set. |
| A source **designates a default** for a parameter or mode | The named authority specifies the choice that applies under stated default conditions. Retain whether those conditions concern equipment, a mode declaration or a message schema. | The current setting of an installed unit. |
| A request **targets** a unit and **asks for** a value | A specific operation seeks a change. Link any acknowledgement or outcome to that operation, not to a free-standing current-value field. | That the request was accepted, applied, or remains effective. A printed example is not even an issued request. |
| A source **reports an effective setting** for a unit at a time | An attributable readback, status report or authoritative as-applied record explicitly gives the value in effect for the identified parameter and subject. Keep the source, value/unit, and time or interval to which it applies. | That the value is still in effect later, or that behavior exactly follows the setting. |

**Current is a judgment about a time, not another stored default.** For the time being asked about, show an effective value only if its source, subject, parameter and temporal applicability are established. A readback supports “reported at T”; continued applicability needs a source validity statement or a documented freshness rule and no contradictory or superseding evidence. Otherwise show “last reported at T” separately, or “current unknown.” Conflicting applicable reports stay visible rather than choosing whichever arrived last. No universal freshness duration is proposed.

**Why these distinctions:** SAPIENT separates registration from status; the Integrated Sensor Architecture separates capability declarations from reported property values; Web of Things describes read and write interactions without asserting that they ran; SensorML separates configurable from configured process descriptions. These sources motivate the relationships. The test for calling a value *current* is our design choice, not a rule attributed to every donor.
