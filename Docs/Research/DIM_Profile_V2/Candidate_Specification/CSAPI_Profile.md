# Candidate application Profile for OGC API – Connected Systems

**Working specification · 31 October 2026.** The binding below is proposed by this project. It selects existing structures in OGC API – Connected Systems (CSAPI), Sensor Model Language (SensorML) and SWE Common. It is not an adopted OGC requirement or a claim that the complete application Profile has been specified.

[Components and channels](#components-and-channels) · [Campbell: temperature of what?](#campbell-temperature-of-what) · [Configuration](#configuration) · [Did the node switch modes?](#did-the-node-switch-modes)

## Components and channels

[Donor terms side by side](../Concept_Donor_Comparison/Donor_Terms_Side_by_Side.md#components-and-channels) · [What the DIM means](DIM.md#components-and-channels) · [Worked SensorML JSON](examples/s31-lb-design.sml.json)

**Proposed rule:** A producer must describe evidenced physical parts separately from outputs and result fields. A client must not count channels, data streams or result fields as physical equipment. When a description identifies the origin of an output, retain that association even if another component exposes the output to the network.

| Information to exchange | Proposed binding | What it must not imply |
|---|---|---|
| **A product design with a sensing part** | Use a CSAPI `Procedure` of sensor-datasheet type. In its `application/sml+json` representation use `PhysicalSystem.components` for this aggregate design, with a named `PhysicalComponent` for the described probe. A project-issued design URI identifies the description, not a deployed unit. | No installation, serial number, deployment time or operational observation follows from the datasheet. No position in a Procedure. |
| **A component's result exposed by the reporting system** | Describe the component output and the outward system output in SensorML `outputs`; when the source supports the flow, connect them with `connections[].source` and `.destination`. For a grouped output, use a named SWE Common `DataRecord`; put each scalar measurement in a `Quantity` field with its own name, property definition and unit. | A record with two fields is not two probes. This describes logical data flow, not the raw on-wire probe protocol or a proved event. |
| **An identified installed system and its operating data** | Link the unit to its datasheet using `systemKind` (`typeOf` in SensorML). When publishing data, a `DataStream` describes one output of one producing System, with a common schema across that stream. For the grouped-output choice, the JSON observation-schema resource uses `obsFormat: application/json` and the two-field `DataRecord` as `resultSchema`; values in `Observation.result` follow it. Separate scalar outputs may instead justify separate streams, with no change to physical inventory. | A data stream is not itself a channel address or a probe. Do not create an individual unit from a model name, an IEEE address or a published example. Part 2 §9.2.2 says the server derives `observedProperties` and related summaries from linked observations, with nulls when none are linked; do not use them to advertise a mere design capability. |
| **Actual subsystem membership or source-specific interface facts** | In the CSAPI Subsystems class, use nested System resources for composition and a `Deployment` for changing aggregation (Part 1 §§10.2–10.5). A current deployed subsystem can also appear in the subsystem listing. Preserve the original module/address context, functional-realization and interface-visibility facts in source mappings; a lossless common wire binding for those extra facts is **not specified here**. | Inline design components do not substitute for required instance endpoints. Cable length does not choose between composition and deployment. Never silently discard an unmapped channel address and declare a round trip lossless. |

### Worked result: S31-LB

This is the [external-probe reference design](https://wiki.dragino.com/docs/LoRaWAN-End-Node/temperature-humidity-sensors/s31-lb/), not the integrated-probe S31B. Open the [example](examples/s31-lb-design.sml.json): it has one `probe`, a component output named `environment`, and a connection to the outward `environment` output. Its two fields denote [air temperature](https://vocab.nerc.ac.uk/standard_name/air_temperature/) and [relative humidity](https://vocab.nerc.ac.uk/standard_name/relative_humidity/). These common field names, grouping, concept URIs and `urn:example:` design identifiers are our mapping choices, not Dragino-issued identifiers. Other node fields, the raw flag, the record timestamp, power and radio hardware are not part of this two-quantity projection; the [source sheet](../Controlled_Corpus/System_Data_Sheets/Dragino_S31_LB.md) retains them.

| Native input | Temperature | Relative humidity | Result for the consumer |
|---|---:|---:|---|
| Published history entry `C-E01` (FPort 3) | bytes 4–5: `01 10` → **27.2 °C** | bytes 2–3: `02 36` → **56.6 % RH** | Result fragment: `{"temperature":27.2,"relativeHumidity":56.6}`. It is an example, **not** an Observation from an authenticated deployment. |
| Documented no-data reply | none | none | **No result**, not `0 °C` and `0 % RH`. |

A Details view could therefore say **“External SHT31 probe — measures air temperature and relative humidity.”** It cannot say which serial-numbered probe is operating or that it has two IEEE channels. Note that FPort 2's decoder labels `TempC_SHT31` and `Hum_SHT31` describe the same two quantity types; the FPort 3 history layout above has different byte positions. Do not reuse offsets from one message type in another.

### Reproduce the check

From a checkout of this branch run `python3 Docs/Research/DIM_Profile_V2/Candidate_Specification/examples/check_s31.py` (Python 3.10+, no dependencies). The [checker](examples/check_s31.py) reads all eight published history entries from the retained [sheet, §4](../Controlled_Corpus/System_Data_Sheets/Dragino_S31_LB.md#4-every-record-in-the-original-published-history-example), compares their decoded values with the recorded expansion, and checks the example design's component, field meanings, units and connection. Negative cases add a fictitious second probe, change humidity to °C, break the connection, supply a no-data reply and truncate an entry. These offline checks passed. They are specific to this example, not a generic Profile validator, a full OGC JSON Schema validation, live interoperability or a test of installed hardware.

## Campbell: temperature of what?

**Could a reader accidentally display 25.91098 °C as outdoor weather?** Yes, if it matches on the word “temperature” or on the unit alone. Here is what the sources support instead. This is a comparison of documents, **not a dashboard from a single station**.

| Equipment / source field | Temperature of what? | What a reader can show |
|---|---|---|
| CR1000X logger · `PanelTemp` · D-S02 | The logger's wiring panel | **25.91098 °C — manufacturer example** |
| ClimaVue 50 · `aR7!` position 8 · D-R08 | The air | **Air temperature — no reading supplied** |
| Same ClimaVue 50 · `aR7!` position 12 · D-R12 | The humidity sensor itself | **Humidity sensor temperature — no reading supplied** |

Campbell supplies the [CR1000X field definition](https://help.campbellsci.com/crbasic/cr1000x/Content/Instructions/StatusTable.htm) and [separate logger message](https://help.campbellsci.com/datalogger-api/mqtt/status.html). The two ClimaVue positions are defined in [the first-generation manual, rev. 08/2024, Table 8-1, printed p. 21](https://s.campbellsci.com/documents/us/manuals/climavue50.pdf#page=25). They are *capabilities*, not null observations, a failed sensor, or zeroes. Nothing ties the example logger to a deployed ClimaVue. The [Campbell system sheet](../Controlled_Corpus/System_Data_Sheets/Campbell_CR1000X_ClimaVue50.md) keeps the sources separate.

**Proposed Profile rule.** Give each measurement field a semantic `definition` that preserves what the quantity concerns, beside its `label` and `uom`. Reuse a suitable existing definition; a new property per device or manufacturer is not needed. Here both manufacturers' air-temperature fields use the same definition as the Dragino example. The two equipment temperatures need different definitions. For a locally defined property where the distinction depends on the kind of object, use `baseProperty` for the characteristic and `objectType` for the kind of thing it applies to. CSAPI makes `objectType` optional; this narrower obligation is our proposal, **not** an OGC-wide rule. A type such as “wiring panel” is not an identifier for an installed panel. Never substitute a recording or reporting device for the observation's subject merely because it sent the value.

See the [side-by-side donor terms and model decision](DIM.md#temperature-of-what); [CSAPI Part 1, §15.2.2, Table 19 and §19.2.8, Table 55](https://docs.ogc.org/is/23-001/23-001.html); [SWE Common 3.0, §§8.2.2–3](https://docs.ogc.org/is/24-014/24-014.html). The [worked JSON](examples/campbell-temperature-roles.json) includes two illustrative property definitions and two separate selected field lists. Its outer wrapper, source keys and evidence labels are project test material, not CSAPI members. The `urn:example:` definitions resolve in the included local dictionary; production identifiers and deployment are not established. A real result would be bound through its own stream's schema, per [CSAPI Part 2 §§9.6–7 and 16.1.4–5](https://docs.ogc.org/is/23-002/23-002.html). No Observation is published here.

**What was checked:** `python3 Docs/Research/DIM_Profile_V2/Candidate_Specification/examples/temperature_preview.py` runs the [same display routine](examples/temperature_preview.py) against the earlier Dragino description and the new Campbell inputs. Source-specific mappings supply the meanings; the routine does not branch on manufacturer. It matches values to fields within their own source and output. Moving the logger example to the weather-instrument context is rejected. This tests how declared information is consumed offline; it does not independently prove the source mappings, validate complete OGC resources, or test Glaux, hardware or a live server.

## Configuration

**Worked result for Dragino S31-LB: “Transmit interval — documented default: 20 minutes; current setting: unknown.”** The [manufacturer manual, §§2.1 and 3.3.1](https://wiki.dragino.com/docs/LoRaWAN-End-Node/temperature-humidity-sensors/s31-lb/#331-set-transmit-interval-time) gives a default of 20 minutes, a set-command example of `AT+TDC=60000` (60 seconds), and a read-command example of `AT+TDC=?` returning `30000` (30 seconds). They are not a chronological sequence for one unit. AT values use milliseconds; the illustrated `01 00 00 3C` downlink uses seconds. This is the configured periodic uplink interval, not an observed packet cadence. [System sheet: C-O03 and C-C01](../Controlled_Corpus/System_Data_Sheets/Dragino_S31_LB.md).

**Candidate exchange rules.** Adopt the following conventions for the [four DIM relationships](DIM.md#which-setting-applies). They are project choices, not new OGC requirements. The [donor table](../Concept_Donor_Comparison/Donor_Terms_Side_by_Side.md#configuration) records where their meanings come from.

| What the producer knows | Where the information goes | What the client may conclude |
|---|---|---|
| **Model supports a setting; manufacturer declares a default** | On the CSAPI datasheet `Procedure`, declare a named SensorML `parameters` entry with meaning and unit. Keep its value unset. Put the published default in a separate `characteristics` group whose `definition` means *documented equipment defaults*; use the same parameter definition URI for its value. Cite the applicable source. Only add constraints explicitly supported by it. | The model supports the setting and has that documented default. An individual that inherits the group inherits a statement about the default, not a report. |
| **An actual write request or acknowledgement exists** | Where Commands are implemented, put the requested value in `Command.parameters` per the `ControlStream` schema. Keep any linked `CommandStatus`, its status code, times and any result separate. Do not generate these resources for a manual example. | “Requested” or “accepted” does not mean “applied.” `COMPLETED` describes a successful operation; use it as as-applied evidence only when the documented operation guarantees the effective value for this target and time, not as perpetual readback. |
| **An actual readback or authoritative effective configuration exists** | For a read implemented as a command, associate the returned `CommandResult.data` with the read request via `CommandStatus.result`; check the stream's `resultSchema` and correct unit. An attributable status output can instead use a `DataStream` and `Observation` when the source actually supports an observation of that property. For a documented, time-scoped instance snapshot, bind the unit's `typeOf` and use `configuration.setValues` for an inherited parameter, or `setModes` for an evidenced mode; retain the applicable source record and validity, not just the bare number. | “Unit U reported value V at T.” Call it current only for a time its evidence covers; receiving a cached reply now does not make it effective now. A snapshot whose provenance is unknown is not readback evidence. |
| **No applicable instance evidence** | Omit the effective value for that parameter. Keep model metadata, illustrative values and any actual request history in their own roles. Do not manufacture a System, status report, Observation, zero, or open-ended validity interval. | “Current setting: unknown.” Show an attributable older value only as last reported, with its time when known. |

**Example: the design description, not an installed System.** This fragment illustrates the proposed role of the group; `urn:example:` identifiers are illustrative vocabulary, not OGC terms or published production identifiers.

```json
{
  "parameters": [{"name":"uplinkInterval","type":"Quantity","definition":"urn:example:setting:periodic-uplink-interval","label":"Periodic uplink interval","uom":{"code":"s"}}],
  "characteristics": [{"definition":"urn:example:role:documented-equipment-defaults","label":"Manufacturer defaults","characteristics":[{"type":"Quantity","definition":"urn:example:setting:periodic-uplink-interval","label":"Default periodic uplink interval","uom":{"code":"s"},"value":1200}]}]
}
```

**Acceptance cases for review (not a runtime test):** The manual alone yields `1200 s` as default and no instance value. Adding an actual request for `60 s` and an acceptance alone still leaves the effective value unknown. A **hypothetical** attributable `30000 ms` response from the identified unit at T supports `30 s` **as of T**, not a change to the model default. A response from a different unit, an undated example, or a superseded report must not populate the current slot. No device was queried in this increment.

**Original binding sources:** [OGC 23-001, Part 1 §13 and §19.2, requirement 100](https://docs.ogc.org/is/23-001/23-001.html); [SensorML 3.0 §§8.2.2.6, 8.2.5, 8.2.9.3, 8.8, 9.1.5.2](https://docs.ogc.org/is/23-000/23-000.html); [SensorML characteristics group schema](https://schemas.opengis.net/sensorML/3.0/json/DescribedObject.json#/$defs/CharacteristicList) and [SWE Common Quantity](https://schemas.opengis.net/sweCommon/3.0/json/Quantity.json); [CSAPI Part 2 §§9.6–9.7, 10.6–10.7, 10.11–10.13 (state-retrieval example), 16.1.8–16.1.10](https://docs.ogc.org/is/23-002/23-002.html). The state report, the request to read, and the mechanism used to carry its result remain distinct.

### Did the node switch modes?

**Report the status of the task and the mode of the node separately.** A SAPIENT `TaskAck` with `task_status = ACCEPTED` means the node agreed to carry out the identified task. It does not say the node has entered the requested mode. A `StatusReport.mode` from that node is direct evidence of the mode it reports at the time of the message content. These are applications of the existing [DIM configuration relationships](DIM.md#which-setting-applies) and [donor status crosswalk](../Concept_Donor_Comparison/Donor_Terms_Side_by_Side.md#task-responses), not new equipment classes.

| What arrived from SAPIENT | Where it belongs in the proposed Profile | What a client may say |
|---|---|---|
| Registration lists a named mode; a `Task` requests it via `command.mode_change`. | Preserve the node-scoped declaration. Map the actual task and its requested mode to `Command.parameters` under the applicable control-stream schema. | “Supported” and “requested,” not “active.” A registered default is not a status report. |
| Matching `TaskAck.task_id` has `task_status = ACCEPTED`. | Link `CommandStatus.statusCode = ACCEPTED` to that command, with a supported `reportTime`. Do not write the target mode into the node’s reported configuration. | “Mode change accepted.” The earlier reported mode and its time remain available; absent any report, the mode is unknown. |
| A later `TaskAck` reports `COMPLETED` or `FAILED` for that same task. | Record the stated task outcome. For an exact, applicable mode-change operation, completion can support an **as-applied inference**; label it as inferred from task completion, not direct readback. CSAPI requires actual execution time for `COMPLETED`: retain the native acknowledgement when that time is unavailable rather than inventing it. A failure does not tell us which mode is active. | “Node reports that the change completed” or “Node reports that the change failed.” Neither alone proves the mode still applies now. |
| A `StatusReport` from the target node names its mode. | Update that node’s last-reported mode and source time. Preserve the separate task outcome. Where the report represents an actual observation of mode, use the configuration reporting binding above, not `CommandStatus` for the mode itself. | “Node reported *follow* at 10:02.” This can be true even when no completion acknowledgement was received. A matching name and nearby time do not prove a particular task caused the state. |

**Worked sequence — illustrative only, not captured traffic.** Assume the node registered the names `default` and `follow`. At 09:59 it reports `default`; at 10:00 it is asked to switch to `follow`; at 10:01 it accepts. At that point the two answers are **Task: accepted. Last reported mode: default at 09:59.** At 10:02 the node reports `follow`. Now the answers are **Task: accepted (no completion report received). Last reported mode: follow at 10:02.** The reports establish different modes at two times, not the exact instant of transition or that the node is ready at full performance.

**Implementation checks.** Correlate the request target with the responding node and the acknowledgement with its `task_id`. Retain status `report_id`, sender and content timestamp. `active_task_id`, when supplied, identifies an executing task; it is not a completion acknowledgement. An older report arriving late must not replace a newer last-reported value; a report from another node cannot update this node. Temporary modes can revert, and the registered `settle_time` describes a transition characteristic, not a live readiness result. For a single-mode node, SAPIENT says to ignore `mode_change`; do not infer a transition or fabricate an acknowledgement code.
