## 1. What was accomplished — plain language

**We now have a stronger candidate DIM manuscript, not merely a donor checklist.** We preserved the five original distinctions and added the information our challenged donors showed we were overlooking. There is more precision about **a real whole sensing System versus an interface participant**, **what a product/model/capability or technical datasheet actually describes**, **declared abilities versus current operation and completed outcomes**, **physical parts versus functions, host relations, manufacturer implementations and addressed channels**, and **whose source, identity, time and authority a client is actually showing**.

The changes matter to a shared Glaux System Resource Details experience because the model must eventually prevent the same error from recurring across manufacturers: a detector option is not proof it is installed; a measurement channel is not a separately managed physical System; a software component or virtual interface is not necessarily a hardware component; an accepted Task is not a completed detection; and an old, estimated, derived or proxy-reported number is not necessarily a current physical measurement.

**No donor was declared the overall chassis.** The **whole equipment-realized sensing subject** remains a provisional research boundary. The donor challenge revealed significant **relations and qualifications**, not a justified set of five or seven new model classes. A finished DIM, Profile and interoperable client require later source-specific evidence and owner-approved scope.

## 3. The five real manuscript improvements

Each revision was first justified in [Step 05 §3](05_Challenge_Reconciliation.md#3-five-candidate-foundation-decisions--retain-qualify-expand-do-not-adopt-yet). It was then inserted under the existing **F-01–F-05** headings in [v0.2 §4](10_Candidate_DIM_Foundation_v0.2_Donor_Challenge.md#4-candidate-concept-meanings-and-their-donor-native-boundaries) rather than declaring five additional classes or rewriting standards-owned terminology.

| Existing candidate meaning | Why v0.1 needed strengthening | Source-specific change now written in v0.2 | Source-to-client mistake it guards against |
| --- | --- | --- | --- |
| **F-01: real individual System** | F-01 already separated a real System from its name and resource, but did not sufficiently confront **whole Sensor versus network participant** or physical scope. | The Open Group SOSA **whole Sensor** and separate Host Platform (C239 Edition 1.1 §4.1.1); SAPIENT `Node/node_id`; ISA virtual Component/CIC and IEEE APP/NCAP/TIM role distinctions are compared **without identifying them as one physical object**. [SOSA04-S01/02; ISA04-S01/03](04_Other_Structural_Challenges.md), [SAPIENT S2-N01](02_SAPIENT_Challenge.md), [IEEE](03_IEEE1451_Challenge.md). | No false physical sensor is created merely because a vendor exposes a Node/processor, or because a source assigns a virtual identifier. |
| **F-02: kind/product description** | “Model,” “type,” “modality,” “capability,” and TEDS were too easy to interpret as one reusable product class. | SAPIENT `NodeType` versus `ConfigurationData.model`; ISA capability declarations; The Open Group SOSA `Product/ProductInstance` linked to a functional `Component_`; IEEE 1451 **Meta TEDS, Transducer Channel TEDS and calibration/performance description** examined by the **specific subject** they characterize. | A product family/allowed capability is not an individual installed configuration, and an IEEE channel description is not automatically a manufacturer's whole-product model. |
| **F-03: Method versus execution** | A supported procedure versus performed event is true but **far too coarse for operationally rich equipment**. | SAPIENT declared capability/modes/StatusReport/Task/TaskAck/Detection; ISA CCD, Property/Observable/Command and actual Status/Event/Request/Response; SOSA System Manager versus Task Manager and BIT results; IEEE TEDS metadata versus live transducer services. Each **source-proven claim stage** remains distinct. | “Mode supported” ≠ “mode active”; “Task accepted” ≠ “Task completed”; “test supported” ≠ “test passed”; a requested command is not an Observation. |
| **F-04: parts/components** | Two-axis whole/part versus independent identity failed to explicitly distinguish **physical, functional, product, channel, host, virtual and managed associations**. | SOSA `SensorComponent, HostPlatform, ProductInstance, ModuleImplementation`; ISA CIC visible/opaque/virtual/transparent/translucent members; SAPIENT `sub_components` versus `dependent_nodes`; IEEE transducer channel versus physical chip and output. These become **qualified candidate relationship perspectives**, not a single tree. | A Smart Citizen software `Component` or multiple channel values must not become multiple physical Systems. A CIC-hidden member is not non-existent equipment. |
| **F-05: representation/proxy** | Subject vs digital resource was correct but lacked enough emphasis on **original source, intermediary/producer, metadata applicability, currentness and claim time**. | SAPIENT envelope/Apex mediation, ISA CIC identity/visibility, SOSA indirect management and DSDM representation layers, IEEE TIM/NCAP/TEDS and WoT technical projection are used to **qualify the reported subject, assertion type, origin, timestamp and authority**. | Cached or relayed status should not be labeled a live measurement; the publisher's ID is not automatically the hardware producer ID. |

**Editorial disposition:** F-01 **RETAIN + QUALIFY**; F-02 **RETAIN + QUALIFY/EXPAND**; F-03 **RETAIN but MATERIALLY INCOMPLETE in v0.1 — EXPAND**; F-04 **RETAIN but MATERIALLY INCOMPLETE in v0.1 — EXPAND**; F-05 **RETAIN + QUALIFY/EXPAND**. **No narrow original distinction was proven false**; this does **not** mean the full DIM is complete or architecture-ready.

## 4. Additional role/relationship questions — and what we deliberately did not invent

The [Step 05 reconciliation](05_Challenge_Reconciliation.md#5-deduplicated-new-meaning-questions--seven-source-flags-are-not-seven-classes) reconciled **seven source-challenger flags** from Steps 02–04 into **five overlapping meaning questions**. They appear in [v0.2 §5.3](10_Candidate_DIM_Foundation_v0.2_Donor_Challenge.md#53-v02-donor-challenge-additional-source-backed-relational-questions-not-declared-properties) as **`Q-DC05-01`–`Q-DC05-05`**, explicitly **not** new classes, extra `REL-11`–`REL-15` properties, approved schema fields or an automatically authorized future task list.

| Candidate research question | Key evidence | Why it matters |
| --- | --- | --- |
| **Q-DC05-01 — declaration vs current state** | SAPIENT Registration/ModeDefinition/StatusReport, ISA CCD and Property Status, IEEE TEDS versus transducer data. | Keep *possible*, *supported*, *selected*, *reported*, *measured* and *current* claims distinct. |
| **Q-DC05-02 — action/task lifecycle** | SAPIENT Task/TaskAck/Detection, ISA Request/Response, SOSA system/task management and BIT. | Avoid unearned inference of execution, success or a detection event. |
| **Q-DC05-03 — transducer channel and metadata scope** | **2024-linked IEEE 1451 Playground**, NIST Meta/Channel/Optional TEDS, corrected [Step 03 §0](03_IEEE1451_Challenge.md#0-corrective-evidence-finding--ieee-1451-is-technically-usable-as-a-dim-donor-28-october-2026). | Find out which **module/channel/physical transducer** a unit, range, uncertainty, calibration, timing or performance datum actually describes. |
| **Q-DC05-04 — whole/part/function/product/host** | Open Group SOSA Edition 1.0 DSDM and Edition 1.1 architecture, CSAPI/SensorML original mappings. | Do not collapse whole physical assembly, function, manufacturer product and hosting into one part relation. |
| **Q-DC05-05 — virtual exposure and provenance** | ISA §4.2.2 composition/CIC/visibility, SAPIENT Apex and SOSA indirect management. | Representation, discoverability, independent taskability and physical existence are distinct questions. |

**Key IEEE correction preserved:** It would be **wrong** to describe IEEE 1451 as unavailable for detailed conceptual donor study. The **IEEE 1451 Playground** publicly provides detailed 2024-linked Meta TEDS, Transducer Channel TEDS and Optional TEDS technical descriptions (including physical units, channel types, calibration, uncertainty, sampling/timing and frequency response), complemented by NIST's implementation literature and IEEE↔WoT/OGC-SWE research. The complete licensed **2024 normative requirements/cardinalities** are a narrower **SOURCE_ACCESS_LIMITED** issue; they do **not** prevent using the technical information responsibly for candidate DIM meaning. This distinction is embedded in [v0.2 §§4.2/4.4, 7.4 and 8.4](10_Candidate_DIM_Foundation_v0.2_Donor_Challenge.md) and [corrected Step 03 §0](03_IEEE1451_Challenge.md).

## 6. What the revised manuscript now helps prevent — but still cannot guarantee

The proposed common Resource Details experience can use these qualifications as **questions that must be answered from source evidence**, not as prefilled UI fields. A **TRSS detector slot** may offer a possible hardware option without proving which detector is physically installed. **OmniSense Core2** reports five transducer labels without five authenticated component IDs; the separate **OmniSense Core5ADS** source reports **15.43 V DC and six distinct diagnostics**, but neither power percentage nor sensor health should be invented. **Smart Citizen Kit 2.3** provides manufacturer equipment design and firmware/software patterns, including one SHT31 chip for temperature/humidity and an AS7331 with UV outputs; its backend software `Component` relationship is not an actual verified board or chip. These source-specific facts and their different evidence standing are in [original Step 11](../Donor_Alignment/11_Source_to_DIM_to_Profile_to_UI_Check.md) and [Step 05's source-to-client seams](05_Challenge_Reconciliation.md#4-cross-donor-seams-what-really-corresponds-and-what-does-not).

**Still incomplete:** full configuration and status models, health/diagnostics, physical part replacement, observation and output/performance detail, quantitative power and communications, deployment/time, commands/control, security and lifetime maintenance are not covered comprehensively by these first five meanings. No final DIM root, module boundaries, formal semantic properties, CSAPI Profile selection/binding/conformance, interoperable producer or production-grade common UI was created. This **is useful foundational research**, not proof of final technical interoperability.
