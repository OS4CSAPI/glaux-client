## 1. Quick recovery in ordinary language

**Original pain point.** TRSS and OmniSense II are both UGS products with substantial overlap in engineering/mission purpose, but vendor descriptions and screens still differ enough to make a faithful common Details view hard. When integrated through CSAPI/SensorML and displayed as generic normalized resource data, the details can appear as lists of identifiers, classifiers, attributes and procedures rather than the rich, operationally useful structure of the original vendor displays. That may arise from a **lossy integration**, a **client's missing semantic knowledge**, or both; do not blame the standard without an actual source-to-encoding-to-view comparison.

**Original proposed remedy.** Identify the larger meaningful category and source-grounded shared conceptual framework—**chassis**—that can accommodate the important details from different vendors; reuse legitimate industry, community, government and standards concepts. Use that to build an **implementation-independent published DIM**, and then a **machine-interpretable CSAPI application Profile** so integrations publish a predictable representation and Profile-aware clients can organize the supplied details in a common but extensible UI. This is a **provisional architecture hypothesis** with a legitimate standards rationale, not a completed proof.

**Desired client result.** Both TRSS and OmniSense should appear inside **one compact Resource Details module** with consistent common navigation and useful details. A TRSS detector selection must not be silently confused with an OmniSense transducer label; its battery **estimate** is not a measured voltage; an equipment System is not a measurement channel, a software Component record or a Procedure. The Profile and client must accommodate source differences, omissions, meaningful specializations and uncertainties instead of inventing identity or collapsing values.

**What the owner saw on 28 October.** The first Smart Citizen page only explained research inside the canvas and **missed the request**. A second, separate page actually rendered source-backed/synthetic JSON information in one shared module; the owner described it as **janky, but on the right path**. This is a **primitive user-facing test** of the hypothesis, **not a validated final UX, DIM, Profile or live CSAPI interchange**. The owner wants to refine **DIM, Profile and prototype together**, using what the displayed data reveals, until each is defensible.

## 4. Exactly what the research contributes to the real objective

**We have demonstrated useful *meaning distinctions* and plausible client grouping**, not delivered the full chassis or complete Profile. The five source-grounded candidates distinguish (1) the individual System from its kind, (2) kind from implemented Method, (3) Method availability from actual execution and result, (4) physical components from channels and from software objects, and (5) the real equipment from digital records and representations. The Smart Citizen case found concrete examples of mistakes those distinctions prevent.

**A key practical finding:** A documented SHT31 with two outputs or AS7331 with UV-A/B/C is **one physical component model with multiple measurement channels**, not five independent physical Systems. The manufacturer's backend **Component** is a **Device–Sensor-definition software join**, not a physical part. These are exactly the kinds of relationships a good DIM/Profile-aware UI must preserve and show usefully.

**The new renderer tests the shared-concept approach:** A rulebook keyed to field-definition terms (not the vendor's name) maps meaning into one common UI; the source-specific detail remains. The rulebook is **provisional TypeScript, not an actual Profile or adopted DIM term registry**. TRSS and OmniSense JSON are synthetic; Smart Citizen is design facts, **not** a downloaded CSAPI System JSON. **There is no actual server-backed profile-aware client interoperation yet**.

**The I11–I12 result:** Approved CSAPI/SensorML capabilities already accommodate several basic concepts, but a correct representation is not sufficient if clients cannot interpret fields or the mapping omits source meaning. The "no confirmed semantic standard gap" finding is **narrow**, and I12 specifically corrected observation-derived DataStream metadata, parent/descendant producing stream associations, nested subsystem permanence, and software/hardware Component conflation. **Do not infer that UI fidelity is solved merely because an OGC carrier exists**.

## 5. The future publications and the missing bridge

**Three distinct outputs matter:** (A) a defensible **published DIM** (implementation-independent meanings/relationships/scope); (B) a **published CSAPI Profile** (selected OGC requirements and justified representation/vocabulary rules, assessable conformance); and (C) a **prototype profile-aware CSAPI client** to prove the UI/UX and integration use cases. The original donor research, case reports and wireframes are evidence along the way, **not publication substitutes**. The [provisional outlines](DIM_Profile_V2_Provisional_Document_Outlines_v0.1_26OCT2026.md) already distinguish A from B, without fixing final concepts/modules.

**Do not wait for every donor to be exhausted, but do not invent a total architecture.** As an individual concept earns support, make it traceably available as **candidate publication content**, not just another research memorandum. Show the exact chain: **vendor source meaning → donor-standard meaning → candidate DIM concept/relationship → proposed Profile carrier/constraints → client UI rendering → fidelity/unknowns**. Only owner-reviewed, evidence-supported meanings should eventually be treated as accepted model text. Only demonstrably necessary, enforceable obligations should become Profile SHALLs. The client can be refined iteratively alongside this process, but an attractive panel is not a normative model argument.

**The wireframe is not an unrelated deliverable.** It is a feedback instrument for the DIM/Profile hypothesis: seeing how a rendered TRSS detector slot differs from an OmniSense transducer or SCK measurement channel helps expose non-equivalences, display needs and missing meaning. The UI categories **Operational / Activity / Commands / Management** are currently design choices, **not** established DIM packages.

**More convincing proof, when the owner requests it**, would involve source-to-CSAPI/System JSON mapping for TRSS and OmniSense under draft Profile conventions, profile-aware client retrieval through a real CSAPI API, comparison with vendor UI information, and explicit **preserved / qualified / missing / misrepresented** checks. Actual field-unit and Observation proof belongs to particular operating claims, not as a prerequisite for every first-pass display experiment. Don't invent hardware or operational records.

2. **No invented final taxonomy or name:** The chassis/domain remains to be *discovered* from source communities and interoperability needs. Source-backed working **equipment-realized sensing System** focus is not a fabricated compound universal class; CSAPI **systemType = Sensor** and **assetType = Equipment** are separate facets. Do not force a V1 "eight subjects" module architecture.
3. **Quarantined model outputs:** Earlier anatomy Phase B/C/D documents that once asserted a “validated” full structure were **quarantined** after audit. They remain historical/research material, **not current adopted class or module authority**, even when their own prose appears decisive. Parent PITON v1.4, its audits and later synthesis describe why.
4. **Donor evidence and edition:** Distinguish OGC CSAPI Parts 1–2, SensorML 3.0, SWE Common, SOSA/SSN (W3C/OGC; 21 October 2026 revision is a Working Draft), **The Open Group SOSA** (different!), SAREF, WoT, OPC UA, AAS, ISA, SAPIENT, OSUS and other donor families. Do not omit a donor by convenience or assert a donor is universally equivalent or implemented simply because a concept aligns.
5. **CSAPI semantic constraints:** **systemKind → one Procedure describing reusable kind/datasheet** vs **procedures → implementable methods**; CSAPI Composition vs Aggregation/Deployment is not UML composition; SensorML config in a Deployment representation is not a base Deployment property. System UID semantics are qualified, not proof of hardware/registration identity. Parent DataStream discoverability can include descendant production and stream content derives from linked actual Observations.
6. **No invented empirical proof:** Historical screenshots, fixture JSON, product design and firmware are **different evidence levels**. A vendor page, example notebook or application estimate is not a verified real System, actual Observation or observed readiness. Source-specific origin, timestamps, units, uncertainty, model/version, producer, installed hardware and raw relationships must survive or remain UNKNOWN.
7. **No forced Profile obligations or UI-derived model classes:** Client rendering is designed from supported meanings, but there is no approved normative Profile. A future requirement must follow established source use and enforceable conformance, not convenience of current JavaScript or layout.
8. **Source privacy/operational sensitivity:** The user furnished screenshots of original MASBUS/MERLIN and vendor screens in this conversation, alongside the October 5 wireframe PDF. Do **not** copy internal operational IDs, network addresses, locations or complete source screenshots into a publicly readable repo simply to improve continuity. Preserve high-level use-case distinctions and refer to stable, already-approved repository wireframe docs. Do not include any credential from prior chat screens in PITONs or GitHub.

The owner requested **this PITON and documentation**, not a future step.
